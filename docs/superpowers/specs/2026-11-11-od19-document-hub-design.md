# เอกสารออกแบบ: ศูนย์บริหารเอกสารแนบ (Document Hub)

- **วันที่:** 2026-11-11
- **โมดูลแรก:** `od19_document_hub`
- **โมดูลในขอบเขต:** `od19_document_hub`, `od19_document_intake`, `od19_document_governance`
- **Branch:** `feature/od19_document_hub` (ตาม AGENTS.md §9)
- **สถานะ:** รอตรวจสอบ (Draft for review)
- **ผู้เกี่ยวข้อง:** ฝ่ายบัญชี / จัดซื้อ / ขาย / HR / ISO / IT

## 1. บทสรุป (Summary)

สร้าง **ชั้นบริหารเอกสารแนบ** ครอบ `ir.attachment` ของ Odoo 19 ให้ครอบคลุมทั้งเอกสารที่ **รับเข้าจากภายนอก** และเอกสารที่ **สร้างจากภายในระบบ** โดยมีเป้าหมายเรียงตามความสำคัญที่ผู้ใช้ยืนยัน (2026-11-11):

| ลำดับ | เป้าหมาย | ตัวชี้วัด |
|---|---|---|
| **4** | ลดงานมือ (intake อัตโนมัติ + จัดหมวดด้วย AI) | ≥ 80% ของเอกสารเข้าถูกจัดหมวดเอง · เวลาต่อเอกสารต่อคนลด ≥ 70% |
| **2** | ค้นหา/ใช้งานเร็ว | ค้นเจอภายใน ≤ 2 วินาที · ค้นได้ทั้งชื่อไฟล์และข้อความในไฟล์ (ไทย) |
| **3** | ธรรมาภิบาล/ตรวจสอบได้ | 100% ของเอกสารสำคัญมี audit การเปิด/ดาวน์โหลด · ทุกหมวดมีนโยบายอายุ |
| **1** | ประหยัดพื้นที่/ค่าใช้จ่าย | วัด dedupe ratio ได้ · ไฟล์กำพร้า = 0 · วัดขนาดแยกหมวด/แผนกได้ |

## 2. ปัญหาและความต้องการ

### 2.1 สถานะปัจจุบัน

| # | เรื่อง | สภาพจริง |
|---|---|---|
| 1 | ปริมาณเอกสารแนบเดิม (Odoo 15) | 169,085 ไฟล์ · ~63 GB · on_filestore 168,911 · in_db 0 · ไม่มี `store_fname` 174 ระเบียน |
| 2 | ที่ย้ายเข้า Odoo 19 แล้ว | 7,379 รายการ (เฉพาะที่ผูกกับข้อมูลที่ย้าย) — คัดลอกไฟล์ + สร้าง `ir_attachment` |
| 3 | เอกสารแนบทั่วไป | ใช้ `ir.attachment` ของ core — **ไม่มี metadata กลาง, ไม่มีหมวด, ไม่มีนโยบายอายุ, ไม่มีคลังเดียวที่ค้นได้** |
| 4 | เอกสารที่สร้างภายใน | PDF จาก QWeb/Jasper และ XML/PDF e-Tax **ไม่ถูกเก็บเข้าแฟ้มอัตโนมัติ** |
| 5 | กำกับดูแล | ไม่มี audit การเปิด/ดาวน์โหลดไฟล์, ไม่มีนโยบายเก็บรักษา/ทำลาย |
| 6 | ประสิทธิภาพ | ไม่มีตัววัดขนาด/dedupe/กำพร้า ระดับที่บริหารได้ |

### 2.2 ข้อเท็จจริงจาก core ที่ต้องใช้ (ตรวจจากซอร์สจริง)

| เรื่อง | หลักฐาน |
|---|---|
| `ir.attachment` มี `checksum` (SHA1, 40) · `file_size` · `mimetype` · `store_fname` (index) · `index_content` | `odoo/addons/base/models/ir_attachment.py:471-481` |
| filestore เป็น **content-addressed ด้วย SHA1** อยู่แล้ว (`_get_path` ใช้ sha1 ของเนื้อไฟล์) | `odoo/addons/base/models/ir_attachment.py:60-76` |
| `_index()` ของ core สกัดข้อความเฉพาะ `text/*` (ASCII `strings`) — **ไม่รองรับ PDF/Office/ไทย** | `odoo/addons/base/models/ir_attachment.py:434-443` |
| `pdfminer.six` มีใน requirements ของโปรเจกต์แล้ว | `requirements-od19.txt:25` |
| `attachment_indexation` เป็นโมดูล **Enterprise** และไม่มีในเช็คเอาต์นี้ | `odoo/addons/` ว่าง · ไม่พบโฟลเดอร์โมดูล |

> **นัยสำคัญ:** เป้าหมายข้อ 1 ไม่ใช่ "สร้าง dedupe ใหม่" แต่เป็น **วัดผล + ลดระเบียนซ้ำ + GC กำพร้า** เพราะชั้นไฟล์ dedupe ให้แล้วโดย core

### 2.3 ความต้องการ

- **R1** เอกสารทุกไฟล์ (เข้า/ออก) ต้องมี metadata กลางชุดเดียวกันและมองเห็นได้จากคลังเดียว
- **R2** เอกสารที่รับเข้าจากภายนอกต้องถูกจัดหมวดอัตโนมัติได้ และมีกล่องรับเข้ารอการยืนยันเมื่อความมั่นใจต่ำ
- **R3** เอกสารที่ระบบสร้างเองต้องถูกเก็บเข้าแฟ้มอัตโนมัติ พร้อมที่มา (โมเดล/เลขที่เอกสาร)
- **R4** ต้องค้นเจอจากทั้งชื่อไฟล์และข้อความในไฟล์ รวมภาษาไทย
- **R5** ต้องมีนโยบายอายุ/เก็บรักษา/ทำลาย และมี audit การเปิด/ดาวน์โหลด
- **R6** ต้องไม่แตะไฟล์ core และต้องไม่ทำให้ประสิทธิ์ระบบตกเมื่อ OCR/AI ทำงาน
- **R7** ต้องแยกการเข้าถึงตามระดับความลับและแผนก
- **R8** ต้องมีตัววัดสุขภาพคลัง (ขนาด/dedupe/กำพร้า/คิวงาน)

### 3.1 ในขอบเขต

| รับเข้า (Inbound) | อัปโหลดยกชุด/ลาก-วาง · โฟลเดอร์เฝ้าดู (พาธบนเซิร์ฟเวอร์) · อีเมลผ่าน alias · พอร์ทัล |

- Object storage ภายนอก (S3/MinIO) — พิจารณาเป็นเฟสท้าย/โมดูลแยก

- การแก้ไฟล์ core ของ Odoo ทุกกรณี
- ระบบลายเซ็นอิเล็กทรอนิกส์ — มีอยู่แล้วที่ `od19_document_sign`

## 4. หลักการออกแบบ

1. **ไม่สร้างที่เก็บไฟล์ใหม่** — ใช้ `ir.attachment` เป็นแหล่งความจริงเดียว เติมชั้น metadata
2. **ไม่แตะ core** — ขยายผ่าน inherit; เพิ่ม DB index ผ่าน `init()` ของโมดูลเรา
3. **ใช้ของเดิมก่อนสร้างใหม่** — `checksum` เดิม, `mail.alias.mixin`, `auditlog`, ไคลเอนต์ AI เดิม
4. **อัตโนมัติต้องหยุดได้** — ทุกช่องทางมีสวิตช์เปิด/ปิด OCR และ AI แยกกัน
5. **งานหนักไม่บล็อกผู้ใช้** — OCR/จัดหมวดทำผ่าน cron แบบเป็นคิว จำกัดขนาด/ประเภท
6. **ยืนยัน 2 จังหวะกับงานทำลาย** — สอดคล้องหลักเดิมของโครงการ
7. **ไทยเป็นหลัก** — label สองภาษาไทย/อังกฤษ และออกแบบสำหรับข้อความไทยโดยเฉพาะ

## 6. โครงสร้างข้อมูล

### 6.1 ฟิลด์ใหม่บน `ir.attachment` (ทั้งหมดขึ้นต้น `od19_`)

| ฟิลด์ | ชนิด | หมายเหตุ |
|---|---|---|
| `od19_category_id` | M2o `od19.document.category` | แกนของการจัดหมวด |
| `od19_origin` | Selection `external` / `internal` / `legacy15` | แยกไฟล์เข้า–ออก |
| `od19_doc_date` | Date | วันที่บนเอกสาร (ไม่ใช่วันที่อัปโหลด) |
| `od19_partner_id` | M2o `res.partner` | คู่ค้าที่เกี่ยวข้อง |
| `od19_department_id` | M2o `hr.department` | แผนกเจ้าของ |
| `od19_confidentiality` | Selection `public`/`internal`/`confidential`/`secret` | คุมการเข้าถึง |
| `od19_retention_policy_id` | M2o `od19.document.retention.policy` | นโยบายอายุ |
| `od19_retention_until` | Date (compute, store) | วันครบกำหนด |
| `od19_legal_hold` | Boolean | ห้ามทำลาย |
| `od19_index_state` | Selection `none`/`pending`/`done`/`failed`/`skipped` | คิวสกัดข้อความ |
| `od19_indexed_at` | Datetime | เวลาที่สกัดสำเร็จ |
| `od19_source_ref` | Char | เลขที่เอกสารต้นทางที่ระบบสร้าง |

> **ไม่สร้าง** ฟิลด์ hash — ใช้ `checksum` (SHA1) ของ core
> ฟิลด์กลุ่มเสี่ยง (`od19_confidentiality`, `od19_legal_hold`) ต้องมี `groups=` และไม่แสดงบนฟอร์มเอกสารแนบปกติ

### 6.2 โมเดลใหม่

| โมเดล | โมดูลเจ้าของ | ฟิลด์หลัก | หน้าที่ |
|---|---|---|---|
| `od19.document.category` | hub | `name`, `code`, `parent_id`, `default_retention_policy_id`, `auto_classify`, `allowed_models` | หมวดเอกสาร (tree) |
| `od19.document.extract` | hub | `attachment_id` (M2o, ondelete cascade, unique), `text_content`, `engine`, `quality`, `lang` | ข้อความที่สกัดได้ — แยกตารางเพื่อไม่ให้ตารางหลักบวม |
| `od19.document.retention.policy` | hub | `name`, `duration_month`, `action` (archive/delete/review), `basis` | **นิยาม**นโยบายเก็บรักษา (ตารางอ้างอิง) — ส่วน**บังคับใช้** (cron/ทำลาย) อยู่ governance |
| `od19.document.channel` | intake | `name`, `kind` (folder/email_alias/portal), `path`/`alias_id`, `default_category_id`, `enable_ocr`, `enable_ai` | ตั้งค่าช่องทางรับเข้า |
| `od19.document.inbox` | intake | `name`, `file` (Binary), `channel_id`, `state`, `suggested_category_id`, `suggested_partner_id`, `confidence`, `attachment_id`, `res_model`, `res_id`, `log` | กล่องรับเข้า (staging) |

### 6.3 ดัชนีที่ต้องสร้าง (ผ่าน `init()` ของโมดูล — ไม่แก้ core)

| ดัชนี | เหตุผล |
|---|---|
| GIN `pg_trgm` บน `od19_document_extract.text_content` | PostgreSQL FTS ตัดคำไทยไม่ได้ — trigram ค้น substring ได้จริง |
| GIN `pg_trgm` บน `ir_attachment.name` | ค้นชื่อไฟล์ภาษาไทยได้เร็วขึ้น |
| btree บน `ir_attachment.od19_category_id`, `od19_retention_until`, `od19_index_state` | ตัวกรองหลักของคลังกลางและ cron |

> ต้องสร้าง extension `pg_trgm` ก่อน (`CREATE EXTENSION IF NOT EXISTS pg_trgm`) — ต้องมีสิทธิ์ระดับ DB

### 6.4 การใช้ของเดิมแทนการสร้างใหม่

| งาน | ใช้ |
|---|---|
| Hash/dedupe ระดับไฟล์ | `ir_attachment.checksum` (มีอยู่) |
| สกัดข้อความ PDF | `pdfminer.six`; ถ้ามี `attachment_indexation` (EE) ให้ใช้ `index_content` ที่ core เติมให้ก่อน |
| ช่องทางอีเมล | `mail.alias.mixin` |
| Audit เปิด/ดาวน์โหลด | OCA `auditlog` (log_read บนกฎของ `ir.attachment`) |
| จัดหมวดด้วย AI | `od19_ai_assistant.lib.client.chat_completion()` |
| ผูก ISO | `od19.iso.document` (M2o บน `ir.attachment`) |

## 7. ส่วนติดต่อผู้ใช้ (UI)

### 7.1 เมนู "ศูนย์เอกสาร"

| เมนู | เนื้อหา |
|---|---|
| คลังกลาง | list/kanban ของ `ir.attachment` + facets + ค้นเนื้อไฟล์ |
| กล่องรับเข้า | kanban ของ `od19.document.inbox` |
| หมวดหมู่ | tree ของ `od19.document.category` |
| นโยบายอายุ | list ของ `od19.document.retention.policy` |
| สุขภาพคลัง | dashboard ตัววัด |

### 7.2 คลังกลาง

- facets: วันที่ · หมวด · คู่ค้า · แผนก · ความลับ · ที่มา · สถานะ index
- แสดงขนาดไฟล์และป้าย "ซ้ำ" เมื่อมี `checksum` เดียวกันมากกว่า 1 ระเบียน
- ปุ่ม "จัดหมวดเป็นชุด" สำหรับเลือกหลายรายการพร้อมกัน
- เปิดดูไฟล์แบบ side panel ไม่ต้องดาวน์โหลด

### 7.3 กล่องรับเข้า (Kanban)

- คอลัมน์ตาม `state`: ใหม่ → กำลังประมวลผล → รอตรวจ → ผูกแล้ว / ปฏิเสธ / ผิดพลาด
- การ์ดแสดงหมวดที่ระบบเสนอ + ค่าความมั่นใจ
- ปุ่ม "ยืนยันและผูก" เปิด wizard เลือกปลายทาง (`res_model`/`res_id`) + หมวด

### 7.4 การเก็บรายงานที่สร้างภายใน

- mixin `_od19_archive_report(binary, meta)` — เฉพาะรายงานที่ประกาศไว้ในทะเบียน
- เรียกหลัง render สำเร็จ: สร้าง attachment `od19_origin=internal` + หมวด + `od19_source_ref`
- เปิด/ปิดเป็นรายรายงาน ไม่เก็บทุกครั้งโดยอัตโนมัติ (กันไฟล์ท่วม)

### 7.5 กำกับดูแล

- หน้าจอ "ครบกำหนด": cron แจ้งเตือน → ทบทวน → archive/delete **ยืนยัน 2 จังหวะ**
- `od19_legal_hold` ระงับการทำลายทันที
- Dashboard: ขนาดรวมต่อหมวด · dedupe ratio · กำพร้า · % จัดหมวดแล้ว · คิว OCR

### 7.6 สิทธิ์

| กลุ่ม | สิทธิ์ |
|---|---|
| `od19_document_hub.group_document_user` | อ่าน/อัปโหลด/จัดหมวดเอกสารที่ตนมีสิทธิ์ |
| `od19_document_hub.group_document_manager` | จัดการหมวด/ช่องทาง/นโยบาย/ผูกปลายทาง |
| `od19_document_hub.group_document_auditor` | อ่าน metadata + audit ทั้งหมด แต่ดาวน์โหลดเฉพาะที่อนุญาต |

ชื่อกลุ่มไม่ชนกับ core และใช้ระบบ record rule กรองตาม `od19_confidentiality` + `od19_department_id`

## 8. ลำดับการทำงาน (Data Flow)

### 8.1 รับเข้าจากภายนอก

```
โฟลเดอร์เฝ้าดู (cron) ─┐
อีเมล (alias)          ├─► od19.document.inbox (state=new)
พอร์ทัล / ลาก-วาง      ┘
        │
        ├─ ตรวจ MIME/ขนาด + คำนวณ checksum + ตั้งชื่อไฟล์มาตรฐาน
        ├─ จัดหมวด: กฎ (ชื่อไฟล์/คู่ค้า/เลขที่เอกสาร) → ถ้าไม่เข้าเกณฑ์ใช้ AI
        ├─ สกัดข้อความ: text layer ก่อน → OCR เฉพาะเมื่อไม่มี text layer
        └─ confidence ≥ 70% → ผูกอัตโนมัติ เป็น attachment
           confidence < 70% → รอคนยืนยันบน Kanban
```

### 8.2 สร้างจากภายใน

```
render รายงานสำเร็จ → _od19_archive_report(binary, meta)
  → สร้าง ir.attachment (od19_origin=internal, หมวด, od19_source_ref)
  → เข้าคิวสกัดข้อความตามปกติ
```

### 8.3 ทำลายตามนโยบาย

```
cron: หา od19_retention_until ≤ วันนี้ และ od19_legal_hold = False
  → แจ้งเตือนผู้รับผิดชอบ → ทบทวน → ยืนยัน 2 จังหวะ → archive/delete
```

## 9. กติกาและการป้องกัน (Guards / Edge cases)

| กรณี | การจัดการ |
|---|---|
| ไฟล์ซ้ำ (checksum + size ตรงกัน) | สร้างระเบียนใหม่แต่ชี้ไฟล์เดียวกัน (ทางเลือก ข. §14) — เก็บร่องรอยการอัปโหลดแต่ละครั้ง, ไม่กินพื้นที่เพิ่มเพราะ core dedupe ชั้นไฟล์ให้แล้ว |
| ไฟล์ใหญ่เกินกำหนด | ข้ามการสกัดข้อความ ตั้ง `od19_index_state=skipped` พร้อมเหตุผลใน log |
| PDF สแกนไม่มี text layer | เข้าคิว OCR |
| OCR/AI ล้มเหลว | `od19_index_state=failed` + ลองซ้ำได้ด้วยปุ่ม/ครบกำหนดครั้งถัดไป |
| ข้อความที่สกัดได้ว่าง | ไม่สร้าง `od19.document.extract` (ไม่ให้ตารางบวม) |
| โฟลเดอร์เฝ้าดูถูกลบ/ไม่มีสิทธิ์ | บันทึกความผิดพลาดที่ช่องทาง ไม่ให้ cron ล้มทั้งรอบ |
| ไฟล์ที่ core ใช้งานอยู่ (เช่น `res_field`) | ห้ามลบ/ย้าย — ตรวจ `res_field` ก่อนทำลาย |
| ไฟล์ที่ขาดจาก filestore | รายงานในสุขภาพคลัง ไม่ raise |
| ผู้ใช้ไม่มีสิทธิ์ระดับความลับ | record rule กรองออกจากผลค้นหา (รวมผลของ auditor) |
| เอกสารที่ถูก post/ล็อก | ไม่ให้แก้ metadata ที่กระทบการเงิน (เฉพาะหมวด/ความลับที่อนุญาต) |

## 13. ความเสี่ยง

| ความเสี่ยง | ระดับ | การบรรเทา |
|---|---|---|
| OCR/AI หนัก ส่งผลประสิทธิภาพระบบ | สูง | เปิดเป็นรายช่องทาง, batch ใน cron, จำกัดขนาด/ประเภท, ทำเฉพาะเมื่อไม่มี text layer |
| ค้นข้อความไทยไม่ครบ | กลาง | ใช้ trigram + ทดสอบกับชื่อไฟล์และเนื้อหาไทยจริงก่อนปิดเฟส |
| จัดหมวดอัตโนมัติผิด | กลาง | เกณฑ์ confidence + คนยืนยันเมื่อต่ำ + เก็บที่มาไว้ตรวจย้อนหลัง |
| เพิ่มดัชนีบนตาราง core | กลาง | สร้างใน `init()` ของโมดูลเรา, ทดสอบเวลาสร้างบน DB ขนาดจริง, ไม่แก้ไฟล์ core |
| นโยบายอายุทำลายผิด | สูง | ยืนยัน 2 จังหวะ + legal hold + ตรวจ `res_field` ก่อนทำลาย + audit ทุกครั้ง |
| ต้องมีสิทธิ์สร้าง extension `pg_trgm` | ต่ำ | ตรวจสิทธิ์ DB ใน P0 (เป็นเงื่อนไขตั้งต้น) |
| ไฟล์ซ้ำปริมาณมากจาก Odoo 15 | กลาง | ทำ P0 baseline ก่อน แล้วตัดสินนโยบาย dedupe ระดับองค์กร |

## 14. เรื่องที่ต้องได้รับการชี้ขาดก่อนเริ่ม P1

มีเพียงเรื่องเดียวที่กระทบโครงสร้างข้อมูลโดยตรง และต้องเป็น **นโยบายระดับองค์กร** ไม่ใช่การตัดสินใจทางเทคนิค:

**นโยบายไฟล์ซ้ำ** — เมื่อพบไฟล์เนื้อเดียวกัน (ค่า `checksum` + `file_size` ตรงกัน) ระบบควรทำอย่างไร

| ทางเลือก | ผลต่อการออกแบบ |
|---|---|
| **ก. ผูกเข้ารายการเดิม** — ไม่สร้างระเบียนใหม่ | ประหยัดระเบียนที่สุด, dedupe ratio ชัดเจน, แต่ต้องมีหน้าจอ "ไฟล์นี้ถูกอ้างอิงจากที่ใด" |
| **ข. สร้างระเบียนใหม่แต่ชี้ไฟล์เดียวกัน** | เก็บร่องรอยการอัปโหลดแต่ละครั้งครบ, dedupe วัดจาก `checksum` ซ้ำ |

**ข้อเสนอของผู้จัดทำ: ทางเลือก ข** — เพราะงานตรวจสอบต้องการร่องรอยว่า "ใครอัปโหลดเมื่อใด" แยกจากกัน ส่วนการประหยัดพื้นที่ได้จากชั้นไฟล์ของ core อยู่แล้ว (D7) และวัด dedupe ratio จาก `checksum` ซ้ำได้โดยไม่เสียร่องรอย

> รอผู้ใช้ยืนยันทางเลือกนี้ก่อนเริ่ม P1 (ถ้าไม่ยืนยัน เอกสารนี้ใช้ทางเลือก ข เป็นค่าตั้งต้น)
