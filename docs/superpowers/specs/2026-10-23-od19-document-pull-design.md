# เอกสารออกแบบ: กลไกกลาง "ดึงเอกสารต้นทาง → รายการเข้าฟอร์ม → ยืนยันก่อนลบ"

- **วันที่:** 2026-10-23
- **โมดูลใหม่:** `od19_document_pull`
- **สถานะ:** รอตรวจสอบ (Draft for review)
- **ผู้เกี่ยวข้อง:** ฝ่ายบัญชี / จัดซื้อ / ขาย / คลังสินค้า

---

## 1. บทสรุป (Summary)

สร้าง **กลไกกลาง** สำหรับทุกฟอร์มที่มีรูปแบบ "เลือกเอกสารต้นทาง → ดึงรายการเข้ามาในฟอร์ม" โดยให้:

1. **ดึงรายการได้ 2 โหมด** — ดึงทั้งหมดตามลำดับเอกสารต้นทาง หรือเลือกรายบรรทัดอย่างอิสระ
2. **ยืนยันก่อนลบ** — เมื่อต้องการลบเอกสารต้นทางออกจากฟอร์ม ระบบต้องเปิดกล่องยืนยันและแสดงรายการที่จะถูกลบก่อนทุกครั้ง
3. **ลบตามรอย (Lineage)** — ลบเฉพาะบรรทัดที่มาจากเอกสารต้นทางนั้นจริง ไม่กระทบบรรทัดที่กรอกเอง
4. **ไม่แตะ Odoo core** — ทั้งหมดเป็นส่วนขยายใน custom module

---

## 2. ปัญหาและความต้องการ (Problem)

### 2.1 สภาพปัจจุบัน

| # | ฟอร์ม | ดึงจาก | ปัญหา |
|---|---|---|---|
| 1 | ใบวางบิลผู้ขาย | ใบสั่งซื้อ (PO) | core ใช้ฟิลด์ `purchase_id` แบบ `store=False` → ล้างตัวเองทันที, ไม่มีกล่องยืนยัน, ไม่มีรายการต้นทางให้จัดการ |
| 2 | ใบวางบิลผู้ขาย | ใบวางบิล/ใบเสร็จเก่า | เชื่อมกับ `purchase_vendor_bill_id` / `invoice_vendor_bill_id` (non-stored) เช่นเดียวกัน |
| 3 | ใบแจ้งหนี้ลูกค้า | ใบสั่งขาย (SO) | มี wizard ของเรา (`od19_sale_wizards`) แต่ **ไม่มีการลบ/ยืนยัน** |
| 4 | ใบสั่งซื้อ (RFQ/PO) | ใบขอซื้อ (PR) | OCA wizard สร้างครั้งเดียว ไม่จัดการที่มาได้ |
| 5 | ใบวางบิลผู้ขาย | ใบรับของ (GRN) | **ยังไม่มี** — core ไม่มี lineage ระดับ picking |
| 6 | ใบแจ้งหนี้ลูกค้า | ใบส่งของ (DO) | **ยังไม่มี** — เช่นเดียวกับข้อ 5 |

### 2.2 ความต้องการของผู้ใช้

- **R1** ทุกฟอร์มที่มี pattern นี้ ต้องใช้กลไกเดียวกัน (consistent)
- **R2** เลือกดึงได้อิสระว่าจะดึงบรรทัดใด หรือดึงทั้งหมดตามลำดับเอกสาร
- **R3** ลบเอกสารต้นทาง → **ต้องถามยืนยันก่อน** → แล้วลบรายการที่ดึงมาให้ด้วย
- **R4** ชื่อ/ลำดับรายการต้องสอดคล้องกับเอกสารต้นทาง
- **R5** ต้องไม่ทำให้ WHT / ภาษี / ราคา ผิดพลาด (ข้อกำหนดสูงสุดของฝ่ายบัญชี)

## 3. ขอบเขต (Scope)

### 3.1 Flow ที่รองรับ (6 flow)

| Flow | เอกสารปลายทาง | เอกสารต้นทาง | สไตล์ | เฟส |
|---|---|---|---|---|
| 1 | ใบวางบิลผู้ขาย (`account.move` in_invoice) | ใบสั่งซื้อ (PO) | A | 1 |
| 2 | ใบวางบิลผู้ขาย | ใบวางบิล/ใบเสร็จเก่า (รวม PO) | A | 1 |
| 3 | ใบแจ้งหนี้ลูกค้า (`account.move` out_invoice) | ใบสั่งขาย (SO) | A | 1 |
| 4 | ใบสั่งซื้อ (RFQ/PO) | ใบขอซื้อ (PR) | A | 1 |
| 5 | ใบวางบิลผู้ขาย | **ใบรับของ (GRN / `stock.picking` incoming)** | B | 2 |
| 6 | ใบแจ้งหนี้ลูกค้า | **ใบส่งของ (DO / `stock.picking` outgoing)** | B | 2 |

### 3.2 สไตล์ A vs B

- **สไตล์ A (ตามปริมาณ):** เอกสารต้นทางคือ PO/SO ดึงเฉพาะบรรทัดที่ `qty_to_invoice > 0` ตาม `invoice_policy` ของสินค้า
- **สไตล์ B (ตามเอกสาร):** เอกสารต้นทางคือใบรับ/ใบส่ง แต่ **ยังกรองผ่านบรรทัด PO/SO** (ผ่าน `stock.move`) เพื่อให้ราคา/ภาษี/WHT ถูกต้อง

> **หลักการสำคัญ:** ใบรับ/ใบส่งไม่มีข้อมูลทางการเงิน จึงต้องย้อนกลับไปที่บรรทัด PO/SO เสมอ B จึงเป็นเพียง "ตัวกรอง" ไม่ใช่แหล่งข้อมูลอิสระ

### 3.3 รายงาน GRNI (Goods Received Not Invoiced)

**อยู่ในขอบเขต เฟส 2** (ผู้ใช้ยืนยัน 2026-10-23) — รายงานแสดงรายการรับของ (GRN ที่ `done`) ที่ยังไม่ถูกวางบิล:

- แหล่งข้อมูล: `stock.picking` (incoming, done) → `stock.move` → `purchase.order.line` เทียบกับ `qty_to_invoice`
- แสดง: เลขที่ใบรับ, วันที่รับ, ผู้ขาย, จำนวนที่รับ, จำนวนที่วางบิลแล้ว, คงค้าง (GRNI)
- ชนิดรายงาน: เริ่มด้วย **Native list/pivot view** (กรองด้วย domain) ก่อน; พิจารณา Jasper ภายหลังถ้าต้องการรูปแบบเฉพาะ
- ขึ้นกับฟิลด์ `od19_source_picking_id` ของสไตล์ B (เฟส 2)

### 3.4 นอกขอบเขต (Out of scope)

- ใบเสร็จรับเงิน / ใบสำคัญจ่าย (payment) — คนละกระบวนการ
- การแก้ไข Odoo core ทุกกรณี
- งานขาย: Blanket Order → SO (พิจารณาภายหลัง)

## 4. หลักการออกแบบ (Design Principles)

1. **ใช้ lineage ที่มีอยู่แล้ว ไม่สร้างซ้ำ** — core เก็บ `purchase_line_id`, `sale_line_ids` ให้แล้ว
2. **ยืนยันฝั่ง server เสมอ** — เพราะ `@api.onchange` ไม่สามารถเด้งกล่องยืนยันได้
3. **Fail-safe** — เอกสารที่ไม่ใช่ Draft ห้ามลบ/แก้
4. **Lean & Maintainable** — กลไกกลางที่เดียว, การผูกโมดูลใหม่ทำผ่าน registry
5. **ไทยเป็นหลัก** — label สองภาษา (ไทย/อังกฤษ) ตามธรรมเนียมเดิมของโครงการ

## 5. สถาปัตยกรรม (Architecture)

### 5.1 โครงสร้างโมดูล

```
custom_addons/od19_document_pull/
├── __manifest__.py          # depends: account, sale, purchase, stock
├── models/
│   ├── od19_document_pull_mixin.py    # ตรรกะกลาง (AbstractModel)
│   ├── od19_document_pull_source.py   # registry ของชนิดเอกสารต้นทาง
│   ├── account_move.py                # ผูก flow 1,2,3,5,6
│   └── account_move_line.py           # ฟิลด์ lineage ระดับ picking (สไตล์ B)
├── wizard/
│   ├── od19_document_pull_wizard.py        # ดึงรายการ (2 โหมด)
│   ├── od19_document_pull_wizard_line.py   # บรรทัดชั่วคราว (checkbox)
│   ├── od19_document_pull_remove_wizard.py # ยืนยันก่อนลบ (2 state)
│   └── od19_document_pull_remove_line.py   # preview บรรทัดที่จะถูกลบ
├── views/
│   ├── account_move_views.xml
│   └── wizard_views.xml
├── security/ir.model.access.csv
├── tests/
└── i18n/th.po
```

### 5.2 การผูกโมดูลอื่น (ไม่บังคับพึ่ง OCA)

| โมดูล | ผูกเพิ่ม | เพราะ |
|---|---|---|
| `od19_document_pull` | `account.move` (flow 1,2,3,5,6) | แกนกลาง |
| `od19_purchase_wizards` | `purchase.order` ← `purchase.request` (flow 4) | โมดูลนี้พึ่ง `purchase_request` อยู่แล้ว จึงไม่บังคับ dependency กับโมดูลกลาง |
| `od19_sale_wizards` | ปรับให้เรียกกลไกกลางแทน | เลิกระบบซ้อน |

> ใช้วิธี **registry** — ปลายทางแต่ละโมเดลประกาศชนิดเอกสารต้นทางของตัวเองเป็น dict โมดูลกลางอ่าน dict นี้เพื่อสร้าง selection/domain ของ wizard อัตโนมัติ

## 6. โครงสร้างข้อมูล (Data Model)

### 6.1 ฟิลด์ใหม่

| โมเดล | ฟิลด์ | ชนิด | หมายเหตุ |
|---|---|---|---|
| `account.move.line` | `od19_source_move_line_id` | Many2one `account.move.line` | เฉพาะ flow 2 — บรรทัดที่ดึงจากใบวางบิลเดิม (core ไม่มี lineage นี้) |
| `account.move.line` | `od19_source_picking_id` | Many2one `stock.picking` | เฉพาะสไตล์ B (เฟส 2) — รู้ว่ามาจากใบรับ/ใบส่งใด |
| `account.move` | `od19_pull_source_label` | Char (computed) | แสดงสรุป "ดึงจาก: PO0001 (5), GRN0002 (2)" |
| `purchase.order` | `od19_pull_source_label` | Char (computed) | แสดงสรุป "ดึงจาก: PR0001 (3)" (flow 4) |

> **หมายเหตุ:** flow 4 ไม่ต้องสร้างฟิลด์ใหม่ — ใช้ `purchase.order.line.purchase_request_lines` (M2m) ที่ OCA `purchase_request` ให้มาแล้ว

### 6.2 ฟิลด์ lineage ที่ใช้ซ้ำจากของเดิม (ไม่สร้างใหม่)

| ปลายทาง | ฟิลด์ | ที่มา |
|---|---|---|
| `account.move.line` ← PO | `purchase_line_id` | core `purchase` |
| `account.move.line` ← SO | `sale_line_ids` | core `sale` |
| `purchase.order.line` ← PR | `purchase_lines` (ฝั่ง PR line) | OCA `purchase_request` |

### 6.3 โมเดลชั่วคราว (Transient)

| โมเดล | หน้าที่ |
|---|---|
| `od19.document.pull.wizard` | เลือกชนิด/เอกสารต้นทาง + โหมด + บรรทัด |
| `od19.document.pull.wizard.line` | บรรทัดให้ติ๊กเลือก (`selected`) |
| `od19.document.pull.remove.wizard` | ยืนยันก่อนลบ (`state`: choose → confirm) |
| `od19.document.pull.remove.line` | preview ว่าบรรทัดใดจะถูกลบ |

## 7. ส่วนติดต่อผู้ใช้ (UI)

### 7.1 ปุ่มบนฟอร์มปลายทาง (แสดงเฉพาะ Draft)

| ปุ่ม | Label (ไทย / อังกฤษ) | การทำงาน |
|---|---|---|
| `action_od19_open_pull_wizard` | ดึงรายการจากเอกสารต้นทาง / Pull Lines from Source | เปิด pull wizard |
| `action_od19_open_remove_wizard` | จัดการ/ลบเอกสารต้นทาง / Manage/Remove Source | เปิด remove wizard |

> ป้ายกำกับทั้งหมดใช้ **สองภาษา ไทย/อังกฤษ** (ผู้ใช้ยืนยัน 2026-10-23) ตามธรรมเนียมเดิมของโครงการ

### 7.2 Pull Wizard

- **ชนิดเอกสารต้นทาง** (Selection) — สร้างจาก registry
- **เอกสารต้นทาง** (Reference) — domain กรอง partner เดียวกัน + สถานะที่ถูกต้อง
- **โหมดการดึง** (Selection)
  - `all_order` = ดึงทั้งหมดตามลำดับเอกสาร
  - `select` = เลือกรายบรรทัด
- **รายการ** — ตาราง checkbox (โหมด `select`) พร้อมคอลัมน์ สินค้า/คำอธิบาย/จำนวนที่วางบิลได้/ราคา/หน่วย
- เมื่อเปลี่ยนเอกสารต้นทาง → ล้างรายการที่เลือกไว้ (กันข้อมูลค้าง)

### 7.3 คอลัมน์ "เอกสารต้นทาง" ในตารางบรรทัด

เพิ่มคอลัมน์แสดงเอกสารต้นทางของแต่ละบรรทัดในตาราง `invoice_line_ids` / `order_line` แบบ **optional** (`optional="show"`) เพื่อความโปร่งใส:

- เนื้อหา: เลขที่เอกสารต้นทาง (เช่น `PO00001`, `GRN00002`) + จำนวนอ้างอิง
- ผู้ใช้เปิด/ปิดคอลัมน์ได้เองผ่านเมนู optional (ไม่รกหน้าจอปกติ)
- ค่าแสดงผลอ่านจาก lineage: `purchase_line_id.order_id`, `sale_line_ids.order_id`, `od19_source_picking_id.name`
- ถ้าเป็นบรรทัดที่กรอกเอง → แสดง `-`

### 7.4 Remove Wizard (ยืนยันก่อนลบ)

- **state = choose:** แสดงรายการเอกสารต้นทางที่ผูกอยู่ในฟอร์ม (แต่ละแถว: ชื่อ + จำนวนบรรทัด) ให้เลือกว่าจะลบอันใด
- **state = confirm:** แสดงตัวอย่าง "เอกสาร X จะถูกลบ N รายการ" พร้อมตาราง preview
- ปุ่ม: `ยืนยันการลบ` / `ยกเลิก`

## 8. ลำดับการทำงาน (Data Flow)

### 8.1 ดึงรายการ
```
กด "ดึงรายการ" → เปิด pull wizard
→ เลือกชนิด + เอกสารต้นทาง
→ เลือกโหมด (ทั้งหมด/เลือกเอง)
→ กด "ดึงรายการ"
→ mixin._od19_pull_apply(source, mode, selected_refs)
   - สร้างบรรทัดปลายทางด้วย prepare ของเอกสารต้นทาง (คงราคา/ภาษี/WHT)
   - ผูก lineage (purchase_line_id / sale_line_ids / od19_source_picking_id)
   - ข้ามบรรทัดที่มีอยู่แล้ว (กันซ้ำ)
   - ตั้ง sequence ตามเอกสารต้นทาง
→ กลับเข้าฟอร์ม พร้อมรายการใหม่
```

### 8.2 ลบเอกสารต้นทาง
```
กด "จัดการ/ลบเอกสารต้นทาง" → เปิด remove wizard
→ เลือกเอกสารต้นทาง (state=choose)
→ แสดง preview บรรทัดที่จะถูกลบ (state=confirm)
→ กด "ยืนยันการลบ"
→ mixin._od19_pull_remove(source)
   - ลบบรรทัดที่ lineage ชี้ไปยังบรรทัดของเอกสารต้นทางนั้น
   - คงบรรทัดที่กรอกเองไว้
```

## 9. กติกาและการป้องกัน (Guards / Edge Cases)

| กรณี | การจัดการ |
|---|---|
| เอกสารปลายทางไม่ใช่ Draft (post แล้ว) | ซ่อนปุ่ม + raise `UserError` ถ้าถูกเรียก |
| ดึงซ้ำ | ข้ามบรรทัดที่มี lineage ซ้ำอยู่แล้ว |
| บรรทัดถูกวางบิลไปบางส่วน | ดึงเฉพาะส่วนที่ `qty_to_invoice > 0` |
| ใบรับ/ใบส่ง หลายรอบต่อ PO 1 ใบ | สไตล์ B รองรับ (เลือกเป็นรอบ) |
| ของตีกลับ/คืนผู้ขาย | ตรวจ `qty_to_invoice` ให้ติดลบ/เป็นศูนย์ → ไม่ขึ้นให้เลือก |
| เอกสารต้นทางถูกลบไปแล้ว | lineage ชี้ของที่หาย → แสดงผลแบบนุ่มนวล ไม่ error |
| ผู้ขายถูกเปลี่ยน | domain ของเอกสารต้นทางกรองตาม partner ปัจจุบัน |
| ลบบรรทัดเองในฟอร์ม | lineage ของบรรทัดนั้นหายไปตามธรรมชาติ (ไม่ต้องทำอะไร) |
