## 1. สรุปสั้น ๆ

Wave 1 ก้อนนี้ออกแบบ "งานขายแบบสัญญาหลัก" ไม่ใช่งานขายแบบขายครั้งเดียวจบ

รูปแบบธุรกิจที่รองรับคือ:

- มี `Master Contract` หรือสัญญาหลักเป็นกรอบเชิงพาณิชย์
- สัญญาเดียวอาจครอบทั้งสินค้าและบริการ
- วงเงินในสัญญาเป็นวงเงินคาดการณ์ ลูกค้าอาจใช้จริงถึงหรือไม่ถึงก็ได้
- ถ้าใช้เกินอาจต้องทำสัญญาแนบท้าย ขึ้นกับกติกาของสัญญานั้น
- จะยังไม่เรียกเก็บเงินจริงจนกว่าจะเกิดกิจกรรมจริงและผ่านเงื่อนไขการวางบิล

พูดง่าย ๆ คือ:
ฝ่ายขายไม่ได้ขายแล้วออกบิลทันที
แต่ขาย "กรอบสัญญา" ก่อน แล้วค่อยตัดใช้จริงจากกิจกรรมสินค้า/บริการทีละรอบ

## 2. เป้าหมายของ Child Spec นี้

Child spec นี้มีเป้าหมายเพื่อกำหนด future-state ของงานขายแบบสัญญาหลักให้ชัดในเรื่องต่อไปนี้:

- โครงสร้างของสัญญาหลักและรายการย่อยภายใต้สัญญา
- วิธีควบคุมวงเงินและนโยบายรายสัญญา
- วิธีเชื่อม "กิจกรรมจริง" ไปสู่ "สิทธิในการวางบิล"
- บทบาทของฝ่ายขาย ฝ่ายปฏิบัติการ ฝ่ายวางบิล และผู้อนุมัติ
- KPI และสัญญาณเตือนที่เจ้าของและผู้บริหารต้องเห็น

ก้อนนี้ตั้งใจให้เป็น baseline ของโดเมน Sales ใน Wave 1 โดยยังไม่ลงลึกงานปฏิบัติการหน้างานหรือบัญชีเต็มรูปแบบ

## 3. ขอบเขตของ Child Spec

### 3.1 สิ่งที่อยู่ในก้อนนี้

- การทำ `Quotation` และการตกลงเงื่อนไขเชิงพาณิชย์ของสัญญาหลัก
- การอนุมัติและเปิดใช้ `Master Contract`
- การตั้งค่านโยบายรายสัญญา เช่น รูปแบบวงเงิน กติกาเกินวงเงิน และรูปแบบรอบบิล
- การสร้างรายการย่อยเมื่อมีการซื้อสินค้า หรือเรียกบริการจริงภายใต้สัญญา
- การกำหนด `billing trigger` จากเอกสารหรือหลักฐานที่ทำให้พร้อมวางบิล
- การควบคุมสถานะจาก "เริ่มสั่งงาน" ไปจนถึง "วางบิลแล้ว"
- รายงานเชิงบริหารที่สะท้อนการใช้วงเงิน ความเสี่ยง และรายได้ค้างวางบิล

### 3.2 สิ่งที่ยังไม่ลงลึกในก้อนนี้

- ขั้นตอนงานบริการภาคสนามแบบละเอียด
- ขั้นตอนงานคลัง การจองสต็อก และการส่งของแบบละเอียด
- logic ทางบัญชีปลายทาง เช่น account mapping, tax mapping, posting, reconciliation
- การออกแบบหน้าจอหรือฟอร์มเอกสารเฉพาะลูกค้าแบบรายกรณี
- การ map ข้อมูลจาก Odoo 15 CE แบบ field-by-field

## 4. Business Model ที่ระบบต้องรองรับ

### 4.1 สัญญาหลักเป็นกรอบทางการค้า

`Master Contract` เป็นข้อตกลงทางการค้า ไม่ใช่การตั้งหนี้ทันที

สิ่งที่สัญญาหลักต้องอธิบายได้อย่างน้อยคือ:

- ลูกค้ารายใด
- ระยะเวลาของสัญญา
- วงเงินตามสัญญา
- ประเภทงานที่อยู่ภายใต้สัญญา
- นโยบายการตัดใช้วงเงิน
- นโยบายการวางบิล
- นโยบายเมื่อใกล้เต็มหรือเกินวงเงิน

### 4.2 สัญญาเดียวรองรับสินค้าและบริการร่วมกันได้

ธุรกิจนี้ต้องรองรับสัญญาที่มีทั้ง:

- รายการสินค้าที่ลูกค้าจะซื้อภายใต้กรอบสัญญา
- รายการบริการที่ลูกค้าจะเรียกใช้ภายใต้กรอบสัญญา

ดังนั้นสัญญาหลักต้องทำหน้าที่เป็น `commercial umbrella` ที่ครอบหลายชนิดกิจกรรมได้

### 4.3 การใช้จริงเกิดเป็นรายการย่อย

เมื่อมีการซื้อสินค้า หรือเรียกบริการจริง ต้องเกิด "รายการย่อยภายใต้สัญญาหลัก" เสมอ

รายการย่อยนี้ทำหน้าที่เป็นจุดเชื่อมระหว่าง:

- สิ่งที่ขายไว้ในกรอบสัญญา
- สิ่งที่ลูกค้าใช้จริงในรอบนั้น
- หลักฐานการส่งมอบหรือการจบงาน
- สิทธิในการวางบิล

### 4.4 สัญญาแนบท้ายเป็นส่วนขยายที่ควบคุมได้

ถ้ายอดใช้จริงเกินกรอบเดิม หรือเงื่อนไขหลักเปลี่ยน ต้องรองรับ `Contract Amendment`

สัญญาแนบท้ายควรใช้สำหรับกรณีเช่น:

- เพิ่มวงเงิน
- ขยายอายุสัญญา
- ปรับเงื่อนไขเชิงพาณิชย์
- ปรับกติกาการวางบิลหรือข้อยกเว้นที่ได้รับอนุมัติ

## 5. Future-State Business Flow

### 5.1 ขั้นที่ 1: Quotation และการเจรจาเชิงพาณิชย์

ฝ่ายขายเริ่มจากการเสนอราคาและตกลงกรอบการค้ากับลูกค้า

ในขั้นนี้ยังไม่เกิดการวางบิล แต่ต้องตกลงเรื่องสำคัญให้ชัด เช่น:

- วงเงิน
- อายุสัญญา
- กลุ่มสินค้า/บริการที่ครอบ
- กติกาเมื่อใกล้เต็มหรือเกินวงเงิน
- รูปแบบการวางบิลรายครั้งหรือรวมรอบ
- เอกสารที่ถือเป็น `billing trigger`

### 5.2 ขั้นที่ 2: อนุมัติและเปิดใช้ Master Contract

เมื่อสัญญาผ่านการอนุมัติ สัญญาจะเข้าสู่สถานะใช้งานจริง

จากจุดนี้ระบบต้องเริ่มควบคุม:

- วงเงินคงเหลือ
- อายุสัญญา
- กติกาการเตือน
- กติกาการอนุมัติข้อยกเว้น
- รอบวางบิล

### 5.3 ขั้นที่ 3: เกิดการใช้จริงภายใต้สัญญา

ทุกครั้งที่ลูกค้ามีการใช้จริง ไม่ว่าจะเป็นสินค้า หรือบริการ ต้องเกิดรายการย่อยที่ผูกกับสัญญาหลัก

รายการย่อยนี้อาจมีเอกสารทางการค้าเพิ่มเติม เช่น:

- ใบเสนอราคาย่อยภายใต้สัญญาหลัก
- เอกสารยืนยันคำสั่งจากลูกค้า
- เอกสารอ้างอิงการสั่งงานภายใน

### 5.4 ขั้นที่ 4: ส่งมอบหรือให้บริการจริง

เมื่อกิจกรรมเกิดขึ้นจริง ต้องมีหลักฐานตามชนิดงาน เช่น:

- สินค้า: ใบส่งของ หรือหลักฐานส่งมอบ
- บริการ: ใบจบงาน หรือ service report

หลักฐานนี้ไม่ใช่เรื่องเอกสารอย่างเดียว แต่เป็นตัวกำหนดว่ารายการนั้น "พร้อมวางบิล" หรือยัง

### 5.5 ขั้นที่ 5: ระบบประเมิน Billing Trigger

ระบบต้องตรวจว่ารายการย่อยนั้นผ่านเงื่อนไขการวางบิลหรือยัง โดยดูจาก:

- policy ของสัญญา
- ประเภทกิจกรรม
- เอกสารหลักฐานที่ได้รับ
- ข้อยกเว้นที่ได้รับอนุมัติ

### 5.6 ขั้นที่ 6: เข้ารอบวางบิล

เมื่อผ่านเงื่อนไข ระบบต้องรองรับ 2 แบบ:

- วางบิลทุกครั้งที่รายการพร้อม
- รวมหลายรายการแล้ววางบิลเป็นรอบตามสัญญา

### 5.7 ขั้นที่ 7: ตัดใช้วงเงินและติดตามสัญญา

ทุกกิจกรรมที่เข้าเงื่อนไขแล้วต้องสะท้อนต่อยอดใช้จริงของสัญญา

เมื่อถึงเวลา ระบบต้องตอบได้ว่า:

- ใช้ไปแล้วเท่าไร
- เหลือเท่าไร
- ใกล้เต็มหรือยัง
- เกินวงเงินหรือยัง
- ต้องทำแนบท้ายหรือไม่
- หมดอายุแล้วปิดตามยอดใช้จริงหรือไม่

## 6. Contract Policy Matrix

หัวใจของก้อนนี้คือ "1 สัญญา = 1 ชุดนโยบายที่ตั้งค่าได้"

### 6.1 รูปแบบวงเงิน

ระบบต้องรองรับอย่างน้อย 2 แบบ:

- `วงเงินรวมเดียว`
  ใช้วงเงินก้อนเดียวครอบทั้งสินค้าและบริการ
- `วงเงินแยกตามหมวด`
  แยกวงเงินย่อย เช่น วงเงินสินค้า และวงเงินบริการ ภายใต้สัญญาเดียว

### 6.2 อายุและสถานะของสัญญา

สัญญาต้องมีอย่างน้อย:

- วันเริ่มต้น
- วันสิ้นสุด
- สถานะ เช่น ร่าง รออนุมัติ ใช้งานอยู่ ปิดแล้ว หมดอายุ
- เหตุผลการปิด เช่น ใช้ครบวงเงิน หมดอายุ หรือปิดตามยอดใช้จริง

### 6.3 กติกาเมื่อใกล้เต็มวงเงิน

ต้องตั้งค่าได้รายสัญญา เช่น:

- เปอร์เซ็นต์เตือน
- ใครได้รับการแจ้งเตือน
- ช่องทางหรือคิวงานที่ต้องไปแสดงผล

### 6.4 กติกาเมื่อเกินวงเงิน

ต้องรองรับนโยบายที่ต่างกันรายสัญญา เช่น:

- เตือนอย่างเดียวแต่ทำรายการต่อได้
- ต้องขออนุมัติก่อนจึงทำรายการต่อได้
- ห้ามเกินเด็ดขาดจนกว่าจะมีแนบท้าย

ทุกกรณีที่เกิดข้อยกเว้นต้องมีร่องรอยว่าใครอนุมัติและเพราะอะไร

### 6.5 รูปแบบการวางบิล

ต้องตั้งค่าได้รายสัญญาอย่างน้อย:

- วางบิลรายครั้ง
- วางบิลรวมรอบ

ถ้าเป็นรวมรอบ ต้องกำหนดรอบอ้างอิงได้ เช่น รายสัปดาห์ รายเดือน หรือรอบเฉพาะที่ตกลงกับลูกค้า

### 6.6 Billing Trigger Policy

สัญญาต้องระบุได้ว่า trigger พื้นฐานของสัญญานี้คืออะไร เช่น:

- ใบส่งของ
- หลักฐานส่งมอบ
- ใบจบงาน
- service report
- หลายแบบร่วมกันตามประเภทกิจกรรม

### 6.7 Amendment Policy

สัญญาต้องรองรับการเพิ่มวงเงินหรือเปลี่ยนเงื่อนไขผ่าน `Contract Amendment`

ระบบต้องมองเห็นความสัมพันธ์ระหว่าง:

- สัญญาหลัก
- แนบท้ายแต่ละฉบับ
- ยอดที่ถูกขยายเพิ่ม
- นโยบายที่ถูกเปลี่ยน

## 7. Billing Trigger Matrix

หลักคิดสำคัญคือ:
`Commercial approval` ไม่เท่ากับ `Billing readiness`

ลูกค้ายืนยันแล้ว ยังไม่ได้แปลว่าวางบิลได้ทันที
จะวางบิลได้เมื่อถึง trigger ที่ policy ของสัญญาหรือรายการย่อยกำหนดไว้

### 7.1 Delivery-based Trigger

ใช้กับรายการที่ผูกกับการส่งมอบสินค้า

เอกสารตัวอย่าง:

- ใบส่งของ
- หลักฐานส่งมอบ
- เอกสารรับของจากลูกค้า

### 7.2 Service-completion Trigger

ใช้กับรายการที่ผูกกับการให้บริการ

เอกสารตัวอย่าง:

- ใบจบงาน
- service report
- เอกสารรับรองงานจากลูกค้า

### 7.3 Mixed Trigger ภายใต้สัญญาเดียว

สัญญาเดียวกันอาจมีทั้งสินค้าและบริการ ดังนั้นระบบต้องรองรับ trigger หลายแบบในสัญญาเดียว โดยดูที่ `รายการย่อย` ไม่ใช่ดูที่สัญญาเพียงระดับเดียว

### 7.4 ระดับการตั้งค่า Trigger

เพื่อให้ยืดหยุ่นพอ ระบบควรรองรับอย่างน้อย 2 ระดับ:

- ค่าเริ่มต้นที่ระดับสัญญา
- ข้อยกเว้นที่ระดับรายการย่อย

### 7.5 สถานะที่ต้องแยกให้ชัด

ระบบต้องแยกสถานะอย่างน้อยดังนี้:

- มีคำสั่งหรือรายการย่อยแล้ว
- เกิดกิจกรรมจริงแล้ว
- มีหลักฐานแล้ว
- พร้อมวางบิลแล้ว
- วางบิลแล้ว

ถ้าไม่แยกสถานะเหล่านี้ ระบบจะตอบไม่ได้ว่างานไหนค้างเอกสาร งานไหนพร้อมวางบิล และงานไหนถูกวางบิลซ้ำ

## 8. Roles and Approval Model

### 8.1 Sales

รับผิดชอบ:

- ทำใบเสนอราคา
- เปิดคำขอสัญญาหลัก
- เปิดรายการย่อยเมื่อมีการใช้จริง
- ติดตามวงเงินและการต่อสัญญา
- ประสานเมื่อจำเป็นต้องทำแนบท้าย

### 8.2 Sales Manager / Commercial Approver

รับผิดชอบ:

- อนุมัติใบเสนอราคาที่เกินกรอบมาตรฐาน
- อนุมัติสัญญาหลัก
- อนุมัติสัญญาแนบท้าย
- อนุมัติกิจกรรมที่เกินวงเงินเมื่อ policy อนุญาต

### 8.3 Operations / Service / Delivery Team

รับผิดชอบ:

- ส่งมอบสินค้า
- ให้บริการ
- ออกหลักฐานการส่งมอบหรือใบจบงาน
- ยืนยันว่ากิจกรรมถึงจุดที่พร้อมเข้าสู่การประเมิน trigger หรือยัง

### 8.4 Customer Confirmation Point

ในเชิง process ต้องมีจุดที่ลูกค้ายืนยันการรับของ รับงาน หรือรับรองผลการบริการในกรณีที่ trigger ของสัญญาต้องใช้หลักฐานจากฝั่งลูกค้า

### 8.5 Billing / Finance Operations

รับผิดชอบ:

- ตรวจความครบถ้วนของหลักฐาน
- ดึงรายการเข้ารอบวางบิล
- วางบิลรายครั้งหรือรวมรอบตามสัญญา
- ป้องกันการวางบิลซ้ำ
- รายงานรายการที่ควรวางบิลแต่ยังติดเงื่อนไข

### 8.6 Owner / Management View

ใช้เพื่อดูภาพรวม ไม่ใช่เพื่อทำรายการรายวัน โดยควรเห็น:

- สัญญาใกล้หมด
- สัญญาใกล้เต็มหรือเกินวงเงิน
- รายได้ค้างวางบิล
- รายการ exception ที่ยังไม่ปิด
- ลูกค้าที่ใช้วงเงินผิดจากคาดมาก

### 8.7 จุดอนุมัติสำคัญ

ก้อนนี้ต้องรองรับการออกแบบ approval อย่างน้อยในจุดต่อไปนี้:

- อนุมัติใบเสนอราคา
- อนุมัติสัญญาหลัก
- อนุมัติแนบท้าย
- อนุมัติเกินวงเงิน
- อนุมัติข้อยกเว้นของ billing trigger
- อนุมัติรอบวางบิลในกรณีที่บริษัทต้องการจุดควบคุมก่อนออก invoice

## 9. Reporting and Owner Value

โดเมนนี้ต้องไม่จบแค่ "ควบคุมเอกสารขาย" แต่ต้องสร้างข้อมูลสำหรับการตัดสินใจ

### 9.1 Contract Portfolio Overview

ผู้บริหารควรเห็นอย่างน้อย:

- มูลค่าสัญญารวม
- มูลค่าที่ใช้จริงแล้ว
- มูลค่าคงเหลือ
- สัญญาใกล้หมดอายุ
- สัญญาใกล้เต็มวงเงิน

### 9.2 Consumption vs Contract

ต้องเปรียบเทียบได้ว่า:

- ลูกค้ารายไหนใช้ต่ำกว่าที่คาด
- ลูกค้ารายไหนใช้เร็วผิดปกติ
- หมวดสินค้า/บริการใดใช้วงเงินมากที่สุด

### 9.3 Billable Backlog

ต้องมองเห็นรายการที่:

- ทำงานแล้วแต่เอกสารยังไม่ครบ
- เอกสารครบแล้วแต่ยังไม่เข้ารอบวางบิล
- ติด approval หรือ exception

นี่คือรายงานที่ชี้ "เงินที่ควรเก็บได้ แต่ยังไม่เก็บ"

### 9.4 Over-limit and Exception Monitor

ต้องมองเห็น:

- รายการใกล้เต็มวงเงิน
- รายการเกินวงเงิน
- รายการที่ใช้ข้อยกเว้น
- รายการที่ควรทำแนบท้ายแต่ยังไม่ทำ

### 9.5 Billing Cycle Performance

ต้องวัดได้อย่างน้อย:

- เวลาจากกิจกรรมจริงถึงพร้อมวางบิล
- เวลาจากพร้อมวางบิลถึงออก invoice
- คอขวดเกิดที่เอกสาร approval หรือรอบบิล

### 9.6 Renewal and Amendment Signals

ต้องมีสัญญาณเตือนอย่างน้อย:

- สัญญาใกล้หมดอายุ
- สัญญาที่มีแนวโน้มใช้เกินเร็ว
- สัญญาที่ควรต่ออายุ
- สัญญาที่ควรทำแนบท้าย

## 10. แนวคิดของข้อมูลหลักในโดเมนนี้

เพื่อให้ child spec นี้แปลงเป็น implementation plan ได้ง่าย ก้อนนี้ควรยึดแนวคิดข้อมูลหลักอย่างน้อยดังนี้:

- `Master Contract`
  ข้อตกลงหลักระดับลูกค้า
- `Contract Policy`
  ชุดกติกาที่ผูกกับสัญญา
- `Contract Amendment`
  เอกสารแนบท้ายหรือการเปลี่ยนเงื่อนไข
- `Contract Consumption Line`
  มุมมองยอดใช้จริงสะสมหรือยอดที่ถูกตัดใช้
- `Contract Activity Order`
  รายการย่อยที่เกิดจากการใช้จริงแต่ละครั้ง
- `Billing Evidence`
  หลักฐานที่ใช้ประเมิน trigger
- `Billing Readiness`
  สถานะความพร้อมวางบิล
- `Billing Batch/Cycle Reference`
  ตัวอ้างอิงกรณีรวมหลายรายการเข้ารอบบิลเดียวกัน

ก้อนนี้ยังไม่บังคับว่าต้องออกแบบเป็น model ใน Odoo อย่างไรทันที แต่กำหนดว่าการออกแบบจริงต้องครอบคลุม concept เหล่านี้

## 11. สมมติฐานและข้อตกลงที่ใช้ในสเปกนี้

child spec นี้ยึดสมมติฐานที่ได้จากการคุยกับผู้ใช้งานดังนี้:

- สัญญาหลัก 1 ฉบับอาจครอบทั้งสินค้าและบริการ
- จุด trigger วางบิลอาจต่างกันตามชนิดกิจกรรม
- การควบคุมเกินวงเงินต้องตั้งได้รายสัญญา
- วงเงินของสัญญาอาจเป็นวงเงินรวมเดียว หรือแยกตามหมวด
- รูปแบบการวางบิลอาจเป็นรายครั้ง หรือรวมรอบ แล้วแต่สัญญา

ถ้าความจริงของบางธุรกิจย่อยต่างจากสมมติฐานนี้ ให้ถือเป็น input สำหรับ child spec ถัดไปหรือ refinement ของก้อนนี้ก่อนลงมือทำแผน

## 12. Deferred Scope

สิ่งต่อไปนี้ควรถูกแตกเป็น child spec หรือ implementation stream ถัดไป:

- `Service Execution Detail`
  รายละเอียดงานบริการหน้างานและเอกสารภาคสนาม
- `Stock / Delivery Execution Detail`
  รายละเอียดงานคลังและการส่งของ
- `Billing Operations Detail`
  การจัดรอบบิล ข้อยกเว้นรอบบิล และคิวงานวางบิลเชิงลึก
- `Accounting Posting Detail`
  การลงบัญชี การ map ภาษี และการ reconcile
- `Legacy Mapping Detail`
  การ mapping จาก Odoo 15 CE แบบ field-by-field

## 13. สิ่งที่ implementation plan ต้องตอบต่อจากสเปกนี้

เมื่อสเปกนี้ได้รับอนุมัติ implementation plan ของก้อนนี้ต้องตอบให้ชัดอย่างน้อยว่า:

- จะใช้ Odoo standard หรือ OCA ตรงไหนก่อน
- ส่วนใดจำเป็นต้อง custom จริง
- bounded context ของ addon จะถูกแบ่งอย่างไร
- approval logic จะถูกทำให้ traceable อย่างไร
- contract policy และ billing trigger จะถูกออกแบบให้เปลี่ยนได้โดยไม่ผูกกับโค้ดแข็งเกินไปอย่างไร
- รายงาน owner/manager ชุดแรกจะมีอะไรบ้าง
- test หลักที่ต้องมีเพื่อคุมความเสี่ยงของโดเมนนี้คืออะไร

## 14. Definition of Done ระดับสเปก

จะถือว่า child spec นี้พร้อมส่งต่อไปขั้นทำแผน เมื่ออย่างน้อยเงื่อนไขต่อไปนี้ครบ:

- ขอบเขตในก้อนนี้และนอกก้อนนี้ชัด
- future-state flow ชัด
- contract policy matrix ชัด
- billing trigger matrix ชัด
- roles และ approval points ชัด
- owner value และ reporting baseline ชัด
- ไม่มีการบังคับวิธีทำเชิงเทคนิคเร็วจนเกินไป
- ไม่ขัดกับหลัก OCA-first, no core modification, และ modular install/uninstall safety
