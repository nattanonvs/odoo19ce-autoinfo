🔐 ส่วนที่ 17 · สิทธิ์และการอนุมัติ

ส่วนนี้ว่าด้วยการควบคุม “ใครเห็นอะไร และใครอนุมัติอะไร” ของทั้งระบบ ตั้งแต่ชั้นสิทธิ์กลาง (บทบาท + ขอบเขตแผนก), แคตตาล็อกบทบาทธุรกิจที่กำหนดไว้ล่วงหน้าประมาณ 44 บทบาท, ศูนย์อนุมัติกลางที่รวมงานค้างอนุมัติจากทุกโมดูลไว้ที่เดียว และศูนย์กลางการแจ้งเตือนที่ส่งข้อความออกได้หลายช่องทางพร้อมกัน (อีเมล, Odoo Inbox และ LINE)

สารบัญส่วนนี้

  1. od19_security_roles — ชั้นควบคุมสิทธิ์กลาง
  2. od19_role_catalog — แคตตาล็อกบทบาทธุรกิจ
  3. od19_approval_center — ศูนย์อนุมัติกลาง
  4. od19_notification_multi_channel — แจ้งเตือนหลายช่องทาง

⬅️ ส่วนนี้รับต่อมาจาก handoff · in

ส่วนที่ 8 · บุคคลฯ (พนักงานใหม่)→ แคตตาล็อกบทบาทธุรกิจ→ ส่วนนี้ (ส่วนที่ 17)

รับพนักงานใหม่/ผู้ใช้ แล้วกำหนดบทบาทและชั้นควบคุมสิทธิ์ก่อนใช้งานทุกโมดูล

➡️ ส่วนนี้ส่งต่อไปยัง handoff · out

ส่วนนี้ (ส่วนที่ 17)→ ศูนย์อนุมัติกลาง→ Handoff Matrix

บทบาทที่ตั้งไว้ควบคุมว่าผู้ใช้เห็น/ทำอะไรได้ในทุกส่วน และเอกสารที่ต้องอนุมัติจะเข้าศูนย์อนุมัติกลาง

od19_security_roles ชั้นควบคุมสิทธิ์กลาง (Access Control Layer)

od19_security_roles เป็น เลเยอร์ที่ 1 ของสถาปัตยกรรมสิทธิ์ในระบบ โมดูลนี้ถูกออกแบบให้ “ไม่รู้จัก” โมดูลธุรกิจใด ๆ จึงติดตั้งได้ก่อนโมดูลอื่นทั้งหมดโดยไม่เกิด dependency วนกัน โดยมีหน้าที่หลักคือ สร้างกลุ่มความปลอดภัยกลางของ OD19, กำหนดขอบเขตข้อมูลตามแผนก และประสานค่าที่นั่ง (Privilege) ให้จัดกลุ่มบทบาทได้อย่างเป็นระเบียบ

วัตถุประสงค์

  • สร้าง Privilege ชื่อ OD19 Roles ไว้จัดกลุ่มบทบาทและกลุ่มสิทธิ์กลางทั้งหมด
  • มีกลุ่มกลาง 4 กลุ่ม ที่ใช้ร่วมกันทุกโมดูล (รายละเอียดด้านล่าง)
  • เก็บ แผนกของผู้ใช้ (od19_department_id) แบบ mirror มาจากแผนกของพนักงาน เพื่อให้เขียน record rule ตามแผนกได้อย่างปลอดภัย
  • มี cron รายวันคอยซ่อมค่าที่นั่ง (mirror) ให้ตรงกับพนักงาน

เมนู

มอดูลนี้ ไม่มีเมนูของตัวเอง — ผลลัพธ์ของมันไปปรากฏในหน้าผู้ใช้ที่ การตั้งค่า › ผู้ใช้และบริษัท › ผู้ใช้ ในแท็บ Access Rights ซึ่งจะเห็น Privilege “OD19 Roles” พร้อมกลุ่มกลาง และบทบาทต่าง ๆ ที่ติดตั้งจาก od19_role_catalog

ฟิลด์สำคัญ

  • od19_department_id — แผนกของผู้ใช้ (อ่านอย่างเดียวในหน้าจอ เพราะถูก mirror มาจากพนักงานอัตโนมัติ)
  • od19_department_code — รหัสแผนก (ดึงมาจากแผนกโดยตรง ไม่เก็บซ้ำ)
  • บน hr.department: เพิ่ม code (รหัสย่อแผนก) และ od19_member_user_ids (ผู้ใช้ที่ผูกขอบเขตกับแผนกนี้)

กลไกการทำงาน

  1. แผนกจากพนักงานคือแหล่งความจริง — เมื่อสร้าง/แก้ไขพนักงาน (hr.employee) ระบบจะดึง department_id มาเขียนลง od19_department_id ของผู้ใช้ที่ผูกอยู่
  2. ซิงก์อัตโนมัติเมื่อเปลี่ยนแผนก/ผู้ใช้ — ถ้าแก้แผนกของพนักงานหรือสลับผู้ใช้ที่ผูก ระบบจะคำนวณและปรับแผนก mirrored ใหม่ให้ทันที
  3. ซิงก์เมื่อผู้ใช้เปลี่ยนบริษัท — การเปลี่ยนบริษัทหลัก/บริษัทที่สังกัดของผู้ใช้จะทริกเกอร์ซิงก์ใหม่เช่นกัน
  4. cron ซ่อมค่าประจำวัน — งาน “OD19: Repair Department Mirror (Users)” รันทุกวันเวลา 03:00 เพื่อกวาดแก้ค่าที่คลาดเคลื่อน (จากการนำเข้าข้อมูลหรือแก้ SQL ตรง)
ค่าที่นั่งถูกออกแบบให้ซิงก์เป็นแบบ idempotent (รันซ้ำได้ผลเท่าเดิม) และกันการเรียกซ้ำด้วย context flag ภายในเมื่อตัวซิงก์เขียนค่ากลับเข้าผู้ใช้

สิทธิ์การเข้าถึง

มอดูลนี้ไม่ได้เพิ่ม ACL ของโมเดลธุรกิจใด (ไฟล์ ir.model.access.csv ไม่มีระเบียน) การคุมสิทธิ์อาศัยกลุ่มกลางข้างต้น และการกำหนดบทบาทให้ผู้ใช้เป็นหลัก โดยการมอบบทบาททำได้ที่หน้าผู้ใช้ (เมนูผู้ใช้ + กลุ่มบทบาท)

ผู้ใช้ใหม่จะได้บทบาท “พนักงานทั่วไป” โดยอัตโนมัติ (ดู od19_role_catalog) ทำให้ถูกจำกัดขอบเขตตามแผนกของตนเองทันที
แผนกในหน้าผู้ใช้เป็น ฟิลด์อ่านอย่างเดียว — อย่าพยายามแก้ตรงนั้น ให้แก้ที่แผนกของพนักงานแทน แล้วรอให้ระบบซิงก์ (หรือรัน cron) เพื่อให้ค่ากลับมาตรงกัน

od19_role_catalog แคตตาล็อกบทบาทธุรกิจ (Business Roles)

od19_role_catalog เป็น เลเยอร์ที่ 2 ทำหน้าที่เก็บเฉพาะ “ข้อมูล” (data only) คือประกาศ บทบาทธุรกิจของบริษัทเป็นระเบียน res.users.role ประมาณ 44 บทบาท แล้วผูกแต่ละบทบาทเข้ากับ กลุ่มสิทธิ์ (User Group) ที่มีอยู่จริงใน Odoo core, OCA และโมดูล OD19 ต่าง ๆ

วัตถุประสงค์

  • รวมบทบาทธุรกิจไว้ที่เดียว เพื่อให้ผู้ดูแลมอบหมายงานให้พนักงานได้ด้วย “ชื่อบทบาท” ที่สื่อความหมาย ไม่ต้องเลือกกลุ่มสิทธิ์ทีละหลายกลุ่ม
  • ผูกแต่ละบทบาทเข้ากับกลุ่มสิทธิ์จริงที่กระจายอยู่ในทุกโมดูล (ฝั่งขาย, จัดซื้อ, คลัง, บัญชี, ISO, รายงาน ฯลฯ)
  • บังคับหลักการ แยกหน้าที่ (Segregation of Duties) เช่น บทบาทที่อนุมัติเครดิตต้องไม่ใช่บทบาทฝ่ายขาย

เมนู

ไม่มีเมนูของตัวเอง — บทบาททั้งหมดแสดงอยู่ใต้ Privilege OD19 Roles ใน การตั้งค่า › ผู้ใช้และบริษัท › ผู้ใช้ (แท็บ Access Rights) โดยผู้ที่มีสิทธิ์ Role Manager จึงจะมอบหมายได้

บทบาทสำคัญที่ควรรู้

บทบาทผูกกับกลุ่มหมายเหตุ
พนักงานทั่วไปbase.group_user · group_od19_department_scopeบทบาทพื้นฐาน มอบให้ผู้ใช้ใหม่ทุกคนอัตโนมัติ (is_default)
ผู้จัดการระบบbase.group_system · base.group_erp_manager · group_od19_department_allดูแลตั้งค่าทั้งระบบ เห็นทุกแผนก
ผู้จัดการการเงินaccount.group_account_manager · group_od19_credit_approverอนุมัติวงเงินเครดิตได้ (คู่กับผู้ตรวจสอบเครดิต)
ผู้ตรวจสอบเครดิตgroup_od19_credit_reviewer · group_od19_credit_approverแยกหน้าที่ — ห้ามมอบให้พนักงานขายคนเดียวกัน
ผู้อำนวยการขาย / จัดซื้อกลุ่ม Director ของเวิร์กโฟลว์ขาย/จัดซื้ออนุมัติเอกสารมูลค่าสูงตามวงเงิน

ขั้นตอน: มอบบทบาทให้พนักงาน

  1. เปิดหน้าผู้ใช้ — ไปที่ การตั้งค่า › ผู้ใช้และบริษัท › ผู้ใช้ แล้วเปิดบัญชีผู้ใช้ที่ต้องการ
  2. เปิดแท็บ Access Rights — หา Privilege OD19 Roles
  3. เลือกบทบาท — ติ๊กบทบาทที่ต้องการ ระบบจะดึงกลุ่มสิทธิ์ที่บทบาท imply มาทั้งชุดให้เอง
  4. บันทึกและตรวจผล — บันทึกแล้วให้ผู้ใช้รีเฟรชหน้า ระบบจะแสดงเมนู/ปุ่มตามสิทธิ์ใหม่

สิทธิ์และหลักการแยกหน้าที่

  • ระเบียนบทบาทถูกตั้งเป็น noupdate="1" — ผู้ดูแลปรับแก้ใน UI ได้ โดยไม่ถูกเขียนทับตอนอัปเกรดโมดูล
  • SoD ด้านเครดิต: บทบาทที่อนุมัติเครดิตได้มีเพียง ผู้ตรวจสอบเครดิต และ ผู้จัดการการเงิน เท่านั้น และต้องไม่มีบทบาทใดให้ทั้งสิทธิ์ฝั่งขายและสิทธิ์อนุมัติเครดิตพร้อมกัน
  • บทบาท ISO หลายตัว imply ทั้ง base.group_user และ base.group_system ตาม ACL จริงของโมดูล ISO
อย่ามอบบทบาท ผู้ตรวจสอบเครดิต หรือ ผู้จัดการการเงิน ให้พนักงานขายคนเดียวกัน — เป็นการละเมิดหลักการแยกหน้าที่ และระบบมีชุดทดสอบคอยตรวจจับการซ้อนทับนี้
มอดูลนี้ต้องติดตั้ง หลังสุด (หลังโมดูลธุรกิจทั้งหมดและหลัง od19_security_roles) เพราะอ้างอิงกลุ่มสิทธิ์ที่กระจายอยู่ทุกโมดูล

od19_approval_center ศูนย์อนุมัติกลาง (Approval Center)

od19_approval_center เป็นแอปที่รวม “งานค้างอนุมัติ” จากหลายโมดูลมาไว้ในที่เดียว เป็นแบบ ตั้งค่าขับเคลื่อน (config-driven) และ อ่านอย่างเดียว (view-only) กล่าวคือ ตัวศูนย์อนุมัติไม่ได้อนุมัติแทน แต่ช่วยให้ผู้อนุมัติมองเห็นว่ารออนุมัติอะไร ใครเป็นผู้ยื่น นานแค่ไหน และคลิกเข้าไปทำงานในเอกสารจริงได้ทันที

วัตถุประสงค์

  • รวมศูนย์งานรออนุมัติจากทุกโมดูล (ค่าใช้จ่าย, ใบขอซื้อ, ISO, ใบสั่งขาย, ขนส่ง, ใบสำคัญจ่าย ฯลฯ)
  • จัดกลุ่มเอกสารให้ผู้อนุมัติ/ผู้ยื่นเห็นเป็น 4 กลุ่ม: รอฉันอนุมัติ กำลังจะมาถึง เสร็จแล้ว ถูกปฏิเสธ
  • เตือนงานค้างเกินกำหนดเวลามาตรฐาน (SLA) เพื่อไม่ให้เอกสารค้างนาน

กลยุทธ์การอ่านสถานะ (strategy)

Field (ฟิลด์บนเอกสาร)

อ่านสถานะจากฟิลด์บนเอกสารโดยตรง เช่น hr.expense หรือ purchase.request ใช้ฟิลด์ state/status เทียบกับค่าที่กำหนดไว้ในแต่ละขั้น

Tier Validation (OCA)

อ่านจาก tier.review ของ OCA — ใช้กับเอกสารที่อนุมัติหลายชั้น เช่น ค่าใช้จ่าย ใบสั่งขาย ขนส่ง

SLA และการเตือนงานค้าง

สถานะ SLAเงื่อนไข
ปกติอายุงานค้างน้อยกว่า SLA
เตือนอายุครบหรือเกิน SLA ที่กำหนด
เกินกำหนดอายุตั้งแต่ 2 เท่าของ SLA ขึ้นไป
ถ้าตั้ง sla_days = 0 หมายถึงแหล่งนั้นไม่คิดการเตือน SLA

ขั้นตอน: เพิ่ม/แก้แหล่งอนุมัติ

  1. เปิดเมนู — ไปที่ การตั้งค่า › Approval Center › Approval Sources
  2. สร้างแหล่งใหม่ — ตั้งชื่อ เลือก Model เป้าหมาย เลือกไอคอน และตั้ง Strategy (Field หรือ Tier Validation)
  3. กำหนดผู้ยื่นเอกสาร — ตั้ง Requester Field และ Requester Kind (User/Employee) พร้อมวันที่ยื่น
  4. กำหนดสถานะสำเร็จ/ปฏิเสธ — กรอก Success States และ Rejected States คั่นด้วยเครื่องหมายจุลภาค
  5. เพิ่มขั้นอนุมัติ (Steps) — ในแท็บ Steps ระบุชื่อขั้น, ฟิลด์สถานะ, ค่าที่รออยู่ และฟิลด์ผู้อนุมัติของขั้นนั้น
  6. ตั้ง SLA และลำดับ — กำหนดจำนวนวัน SLA และลำดับการแสดง แล้วบันทึก
ขั้นที่เว้น Approver Field ว่างไว้จะกลายเป็นขั้นแบบ “คลังรวม” ที่ผู้ใช้ภายในทุกคนเห็นและเข้าถึงได้
ค่าในช่อง Success/Rejected States ต้องตรงกับค่าสถานะจริงของโมเดลนั้น (สะกดตามฟิลด์จริง) มิฉะนั้นเอกสารจะไม่ถูกจัดกลุ่มถูกต้อง

⬅️ รับต่อจาก: เอกสารที่ต้องอนุมัติจากทุกฝ่าย (วงเงิน–ชั้นอนุมัติ) handoff · in

ส่วนที่ 5 · อนุมัติวงเงินขาย→ ส่วนที่ 6 · อนุมัติจัดซื้อ→ ศูนย์อนุมัติกลาง (ที่นี่)

เอกสารที่ต้องอนุมัติจากทุกฝ่าย (อนุมัติวงเงินขายและอนุมัติจัดซื้อตามวงเงิน–ชั้นอนุมัติ) จะถูกรวมไว้ที่ศูนย์อนุมัติกลางแห่งนี้

od19_notification_multi_channel ศูนย์กลางแจ้งเตือนหลายช่องทาง

od19_notification_multi_channel เป็นประตูกลางสำหรับส่งข้อความแจ้งเตือนออกได้พร้อมกันหลายช่องทาง ได้แก่ อีเมล, Odoo Inbox และ LINE โดยเลือกช่องทางตาม “ความชอบของผู้ใช้แต่ละคน” และทำงานผ่านคิว (Queue) ที่ส่งโดยงานเบื้องหลัง พร้อมลองส่งซ้ำเมื่อล้มเหลว

วัตถุประสงค์

  • ให้โมดูลอื่นเรียกบริการเดียวเพื่อแจ้งเตือนได้หลายช่องทางพร้อมกัน
  • ให้ผู้ใช้กำหนดความชอบ (Preference) ว่าอยากรับการแจ้งเตือนเรื่องใด ผ่านช่องทางใด
  • เก็บข้อความลงคิวและส่งแบบเบื้องหลัง เพื่อไม่ให้หน้าจอค้าง และมีกลไกลองส่งซ้ำอัตโนมัติ

อยู่ภายใต้ การตั้งค่า › Notifications

เมนูย่อยใช้ทำอะไร
Channelsดูรายการช่องทาง (อีเมล / Odoo Inbox / LINE) — แก้ไขได้เฉพาะผู้ดูแลระบบ
My Preferencesตั้งความชอบการรับแจ้งเตือนของตนเอง (เห็นเฉพาะรายการของตัวเอง)
Queueคิวการส่งข้อความ ดูสถานะ pending/sending/sent/failed และสั่งส่งใหม่ได้

ช่องทาง (Channels)

ช่องทางคำอธิบาย
Emailส่งอีเมลผ่านแม่แบบ “Notification Multi-Channel: Email” (ต้องมีอีเมลของผู้รับ)
Odoo Inboxแจ้งเตือนภายใน Odoo (กระดิ่ง/กล่องข้อความ) ให้ผู้รับภายในระบบ
LINEส่งข้อความผ่าน LINE Messaging API (ต้องเปิดใช้และตั้งค่าโทเคนที่ระดับบริษัท)

ความชอบการแจ้งเตือน (Preferences)

แต่ละรายการผูก “ผู้ใช้ + เหตุการณ์ (Event)” เข้ากับชุดช่องทางที่ต้องการ โดยมีเหตุการณ์ที่รองรับ เช่น Default, แจ้งเตือนครบกำหนดยืม/เกินกำหนดคืนทรัพย์สิน, ครบกำหนดสอบเทียบ, มอบหมาย/อัปเดตงาน, ประกาศ (Announcement) และ Custom

ถ้าผู้ใช้ไม่ได้ตั้งค่าสำหรับเหตุการณ์นั้น ระบบจะถอยไปใช้ “Default” ของผู้ใช้เอง และถ้ายังไม่มีจึงใช้ Odoo Inbox เป็นค่าตั้งต้น

สถานะของคิวการส่ง

pending → sending → sent / failed
สถานะความหมาย
Pendingรอในคิว ให้ cron ดึงไปส่ง
Sendingกำลังส่ง
Sentส่งสำเร็จแล้ว
Failedส่งล้มเหลว พร้อมข้อความข้อผิดพลาด และจะลองซ้ำอัตโนมัติ (ไม่เกิน 3 ครั้ง)

ขั้นตอน: ตั้งค่าช่องทาง LINE

  1. เปิดใช้ที่ระดับบริษัท — ไปที่หน้าบริษัท (ต้องเป็นผู้ดูแลระบบ) กลุ่ม “LINE Notifications” แล้วติ๊ก Enable LINE Notifications
  2. กรอกโทเคนและซีเคร็ต — กรอก LINE Channel Access Token และ LINE Channel Secret (ช่องแบบรหัสผ่าน)
  3. เลือกช่อง LINE เริ่มต้น — เลือก Default LINE Channel
  4. ผูก LINE User ID ให้ผู้รับ — เปิดหน้าผู้ติดต่อ (res.partner) กรอก LINE User ID ของผู้รับ
  5. ตั้งความชอบของผู้ใช้ — ที่ การตั้งค่า › Notifications › My Preferences เลือกเหตุการณ์และติ๊กช่อง LINE

กลไกการทำงาน

  1. โมดูลอื่นเรียกบริการ — เรียก notification.service.notify(...) พร้อมผู้รับ ข้อความ เหตุการณ์ และหัวข้อ
  2. กระจายลงคิวตามความชอบ — ระบบอ่านช่องทางของผู้รับแต่ละคน แล้วสร้างระเบียนลงคิวทีละช่องทาง
  3. cron ส่งทุก 5 นาที — งาน “Process Notification Queue” ดึงคิวที่ pending ไปส่ง (ครั้งละไม่เกิน 100 รายการ)
  4. ลองซ้ำเมื่อล้มเหลว — รายการที่ failed จะถูกลองส่งใหม่ได้ถึง 3 ครั้ง ส่วนข้อความ LINE จะถูกตัดแท็ก HTML ออกก่อนส่ง
