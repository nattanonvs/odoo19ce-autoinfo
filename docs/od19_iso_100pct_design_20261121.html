ไม่สร้างโมดูลใหม่ แก้ที่ od19.iso.dar โดยตรง (ต่อยอด state machine เดิม 4 ขั้น: draft → review → approval → final_approval → approved)

3.4 ผลหลังอนุมัติ — อัปเดต _apply_approval_effect() (idempotent ผ่าน effect_applied)

request_typeผลอัตโนมัติเมื่อ status = approved
newเปิด wizard od19.iso.dar.create.document (คงเดิม) → ได้เอกสาร Rev.00
revisedocument.action_new_revision_keep_approved() (คงเดิม) + trigger WP2.4 แจ้งเปลี่ยนฉบับพิมพ์
obsoletemark obsolete เอกสาร (คงเดิม) + ยกเลิก/เรียกคืนสำเนาที่ค้างทั้งหมด
copy_controlled/uncontrolledสร้าง copy.record (คงเดิม) — เก็บเพื่อ Backward-compat
change_distributionสร้าง od19.iso.distribution.list เวอร์ชันใหม่ (revision snapshot) + set ตัวเก่าเป็น superseded
printสร้าง od19.iso.print.request (state=draft→auto-submit) + copies_count สำเนา
broad_distributionสร้าง distribution.line ให้ target_holder_ids + สร้าง print.request แบบ uncontrolled (ถ้าต้องพิมพ์)
new_with_printสร้างเอกสารใหม่ (เหมือน new) แล้วต่อด้วย print.request ในใบเดียว
revise_with_printเพิ่ม revision (เหมือน revise) แล้วต่อด้วย print.request ในใบเดียว

3.5 Approval Source (ต่อกับ od19_approval_center)

เพิ่ม record ใน data/approval_source_data.xml สำหรับโมเดล od19.iso.dar ให้แต่ละ request_type กำหนดชุด approver ได้ (reviewer → approver → final_approver) — สำหรับ DAR ที่ต้องผ่านศูนย์อนุมัติรวม

3.7 Tests (WP1)

  • สร้าง DAR ทุก type → ตรวจ required field (document/print) ถูกต้อง
  • อนุมัติ print → มี print.request เกิดขึ้น 1 ใบ, effect_applied=True, อนุมัติซ้ำไม่มีผลซ้ำ
  • อนุมัติ change_distribution → distribution list ใหม่เกิด, ของเก่า superseded
  • อนุมัติ revise → revision +1 และ issued copies ของ revision เก่าถูกตั้ง replacement_pending
Acceptance Criteria (WP1)
  • มี request_type ครบ 9 ค่า และ UI แสดงปุ่ม/ฟิลด์ตามประเภทถูกต้อง
  • ทุก type เดิน 4 ขั้นอนุมัติได้ และมี effect ตรงตามตาราง 3.4
  • Unit tests ผ่าน ≥ 12 เคส (ครอบคลุม effect ของทุก type + idempotency)

4.6 State Machines

print.request :  draft ─▶ review ─▶ approved ─▶ printed ─▶ (done)
                    └──────────────────────▶ cancelled

print.copy    :  reserved ─▶ issued ─┬─▶ returned
                                      ├─▶ replaced   (มี revision ใหม่ → replaced_by_id)
                                      ├─▶ destroyed  (ทำลายตามระเบียบ)
                                      └─▶ lost

distribution.list :  draft ─▶ active ─▶ superseded (มี revision ใหม่)

4.7 Logic สำคัญ (G1 + G2)

  • สร้างสำเนา: เมื่อ print.request → approved ให้ generate copies_count แถว print.copy (state=reserved) พร้อมเลขสำเนารัน
  • จ่ายสำเนา (issue): wizard เลือกผู้ถือครอง → set holder, issue_date, state=issued, พิมพ์ใบนำส่ง/ตราประทับ
  • คืนสำเนา (return): set return_date, state=returned + log
  • เปลี่ยนเมื่อมี Revision ใหม่ (หัวใจ G1): hook _on_document_revision_change(document, new_revision) → หา print.copy ที่ state=issued ของ revision เก่า → สร้าง print.request(request_type=replace_revision) อัตโนมัติ + แจ้ง DCC/ผู้ถือครอง
  • ทำลาย/สูญหาย: บันทึก state=destroyed/lost + เหตุผล (audit)
  • Cron แจ้งเตือนคืนเกินกำหนด: _cron_copy_return_overdue() — แจ้งผู้ถือครอง + DCC

9 · ความเสี่ยง & ข้อตัดสินใจ

ประเด็นผลกระทบข้อเสนอ
Dependency directionถ้า print_control พึ่ง dar จะเกิด cyclefix ทิศทาง: document_control → print_control → dar
ของเดิม copy.record ใน DARซ้ำกับ print.copyคงไว้ backward-compat + map ไป print.copy เมื่ออนุมัติ (ไม่ลบของเดิม)
BDR (แจกกว้าง)ผู้รับเยอะ อาจบันทึกทีละคนไม่ไหวใช้ distribution.line + target_holder_ids เป็นชุด ไม่สร้าง copy ต่อคนจนกว่าจะพิมพ์จริง
Merge PDF เนื้อหาเอกสารต้องใช้ไลบรารีรวมไฟล์เฟสแรกทำ Cover/History/Distribution เป็นหน้าแยก แล้วแนบไฟล์เนื้อหาเดิม (merge ทีหลัง)
การเลือก Variant UIกระทบหน้าจอที่จะ implementรอผู้ใช้อนุมัติ M2 และ M5 (A/B/ทั้งคู่)

  • เลือก Variant: M2 Print Register (A / B / ทั้งคู่) และ M5 Dashboard (A / B / ทั้งคู่)
