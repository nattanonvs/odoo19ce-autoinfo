---

## 1. วัตถุประสงค์ (Purpose)

1.1 เพื่อกำหนดหลักการและทิศทางด้านความปลอดภัยสารสนเทศของบริษัทอย่างเป็นทางการและบังคับใช้ทั่วทั้งองค์กร

1.2 เพื่อคุ้มครองความลับ (Confidentiality) ความถูกต้องครบถ้วน (Integrity) และความพร้อมใช้งาน (Availability) ของข้อมูลและระบบสารสนเทศ

1.3 เพื่อป้องกันการโจรกรรมข้อมูล ข้อมูลรั่วไหล การโจมตีทำลายระบบ การนำเข้าซอฟต์แวร์/โค้ดอันตราย และการเข้าถึงโดยไม่ได้รับอนุญาต ทั้งจากช่องทางออนไลน์และออฟไลน์

1.4 เพื่อให้เป็นไปตามข้อกำหนดของกฎหมาย ข้อบังคับ และมาตรฐานที่เกี่ยวข้อง (รวมถึง PDPA และมาตรฐานสากล ISO/IEC 27001)

1.5 เพื่อสร้างความเชื่อมั่นต่อลูกค้า คู่ค้า และผู้มีส่วนได้ส่วนเสียว่าบริษัทบริหารจัดการความเสี่ยงด้านสารสนเทศอย่างมีระบบ

---

## 2. ขอบเขต (Scope)

2.1 **ขอบเขตภายใน** — ระบบสารสนเทศทุกตัว พนักงานทุกคน ผู้รับเหมา ที่ปรึกษา และผู้ให้บริการภายนอกที่เข้าถึงระบบหรือข้อมูลของบริษัท

2.2 **ขอบเขตทรัพย์สิน** — ฮาร์ดแวร์ ซอฟต์แวร์ เครือข่าย ฐานข้อมูล บัญชีผู้ใช้ เอกสาร ข้อมูล และโมดูลที่พัฒนาขึ้นเอง (`custom_addons/`, `od19_*`)

2.3 **ขอบเขตช่องทาง** — ทั้งช่องทางออนไลน์ (เว็บ, Portal, API, VPN, อีเมล) และออฟไลน์ (เครือข่ายภายใน, อุปกรณ์พกพา, สื่อบันทึกข้อมูล, การเข้าถึงทางกายภาพ)

2.4 **ยกเว้น** — ระบบของบุคคลที่สามที่บริษัทไม่มีอำนาจควบคุม ให้ใช้การประเมินความเสี่ยงของซัพพลายเออร์แทน (ดูข้อ 6.12)

---

## 3. คำนิยาม (Definitions)

| คำ | ความหมาย |
|---|---|
| สินทรัพย์สารสนเทศ | ข้อมูล ระบบ ฮาร์ดแวร์ ซอฟต์แวร์ และบุคลากรที่เกี่ยวข้องกับสารสนเทศ |
| ชั้นข้อมูล | การจำแนกระดับความลับของข้อมูล (Public / Internal / Confidential / Secret) |
| Zero Trust | หลักการไม่เชื่อทุกอุปกรณ์/ผู้ใช้โดยปริยาย ต้องพิสูจน์ตัวตนและให้สิทธิ์น้อยที่สุดเสมอ |
| MFA | การยืนยันตัวตนหลายปัจจัย |
| RBAC | การควบคุมสิทธิ์ตามบทบาทหน้าที่ |
| Incident | เหตุการณ์ด้านความปลอดภัยที่ส่งผลหรืออาจส่งผลกระทบต่อข้อมูลหรือระบบ |
| PDPA | พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล |

## 4. หลักการพื้นฐานของนโยบาย

4.1 **Zero Trust** — ไม่เชื่อถือโดยปริยาย แม้อยู่ในเครือข่ายภายใน ต้องยืนยันตัวตนและให้สิทธิ์น้อยที่สุดเสมอ

4.2 **Defense in Depth** — ป้องกันหลายชั้น (เครือข่าย → ตัวตน → เครื่อง → แอปพลิเคชัน → ข้อมูล) เพื่อให้หากชั้นหนึ่งล้มเหลว ชั้นอื่นยังคุ้มครองได้

4.3 **Least Privilege** — ให้สิทธิ์เท่าที่จำเป็นต่อหน้าที่ และถอนทันทีเมื่อพ้นหน้าที่

4.4 **Assume Breach** — ออกแบบเสมือนว่าระบบอาจถูกเจาะได้เสมอ ต้องมีบันทึกเหตุการณ์ การตรวจจับ และแผนกู้คืนที่พร้อมใช้

4.5 **Risk-Based** — จัดลำดับความสำคัญของมาตรการตามระดับความเสี่ยง (โอกาส × ผลกระทบ)

4.6 **Accountability** — ทุกการกระทำสำคัญต้องตรวจสอบย้อนกลับได้ (Auditability)

## 5. บทบาทและความรับผิดชอบ (Roles & Responsibilities)

| บทบาท | ความรับผิดชอบหลัก |
|---|---|
| ผู้บริหารสูงสุด (CEO) | อนุมัตินโยบาย จัดสรรทรัพยากร สนับสนุนวัฒนธรรมความปลอดภัย |
| ผู้ดูแลความปลอดภัยสารสนเทศ (ISO/ผู้ที่ได้รับมอบหมาย) | กำกับนโยบาย ประเมินความเสี่ยง ตรวจสอบ ควบคุมเหตุการณ์ รายงานผู้บริหาร |
| ผู้ดูแลระบบสารสนเทศ (IT Administrator) | ติดตั้ง ปรับแต่ง ดูแลระบบ เครือข่าย สำรองข้อมูล และบังคับใช้มาตรการทางเทคนิค |
| เจ้าของระบบ/ข้อมูล (System/Data Owner) | กำหนดระดับความลับของข้อมูลและสิทธิ์การเข้าถึงในขอบเขตที่รับผิดชอบ |
| หัวหน้าแผนก | กำกับพนักงานอนุมัติสิทธิ์สุทธิตามหน้าที่ และรายงานเหตุการณ์ |
| พนักงานทุกคน | ปฏิบัติตามนโยบาย ใช้ทรัพยากรอย่างเหมาะสม รายงานเหตุการณ์ทันที |
| ผู้ให้บริการภายนอก/ผู้รับเหมา | ปฏิบัติตามนโยบายเทียบเท่าพนักงาน ภายใต้ข้อตกลงที่กำหนด |

## 6. นโยบายเฉพาะด้าน (Sub-Policies)

### 6.1 นโยบายความมั่นคงปลอดภัยสารสนเทศโดยรวม

- บริษัทกำหนดให้ความมั่นคงปลอดภัยสารสนเทศเป็นความรับผิดชอบร่วมกันของทุกคน
- มาตรการทางเทคนิค กระบวนการ และบุคลากร ต้องสอดคล้องกันและได้รับการทบทวนสม่ำเสมอ
- ทุกโครงการ/การเปลี่ยนแปลงระบบต้องผ่านการประเมินความปลอดภัยก่อนนำขึ้นใช้งาน (Security by Design)

### 6.2 นโยบายการควบคุมการเข้าถึง (Access Control)

- บังคับใช้หลัก **Least Privilege** และ **Need-to-Know**
- ใช้ **RBAC** ผ่านระบบบทบาท (เช่น OCA `base_user_role`) ห้ามให้สิทธิ์รายบุคคลซ้ำซ้อนโดยไม่จำเป็น
- **ห้าม** ใช้บัญชีผู้ดูแลระบบ (`admin`) หรือบัญชีส่วนกลาง (Generic Account) ทำงานประจำวัน ให้แยกบัญชีต่อบุคคล
- **ห้าม** เปิดเผย แลกเปลี่ยน หรือฝากรหัสผ่านร่วมกัน
- บัญชีผู้ใช้ระดับผู้ดูแลระบบ ต้องได้รับการอนุมัติจากผู้บริหารและมีจำนวนจำกัด
- **ทบทวนสิทธิ์** เป็นรอบอย่างน้อยทุก 6 เดือน และทันทีเมื่อพนักงานเปลี่ยนหน้าที่
- **Offboarding** — ระงับบัญชีและถอนสิทธิ์ทันทีเมื่อพ้นสภาพ/ลาออก/ถูกพักงาน (ตาม Checklist)
- บัญชีระบบอัตโนมัติ (service account) ต้องมีเจ้าของชัดเจน หมุนรหัสตามรอบ และห้ามฝัง credential ในโค้ด

### 6.3 นโยบายรหัสผ่านและการยืนยันตัวตน (Password & Authentication)

- บังคับ **MFA** สำหรับบัญชีผู้ดูแลระบบ บัญชีที่เข้าถึงฐานการเงิน และบัญชีที่เข้าใช้งานจากภายนอก
- รหัสผ่านต้องมีความยาวและความซับซ้อนตามที่กำหนด ห้ามใช้รหัสผ่านซ้ำกับระบบอื่น
- เปลี่ยนรหัสผ่านทันทีเมื่อสงสัยว่ารั่วไหล
- บังคับใช้ HTTPS และ HSTS ทั้งหมด ป้องกันการดักจับข้อมูลยืนยันตัวตน
- กำหนดอายุ Session และบังคับออกจากระบบอัตโนมัติเมื่อไม่มีการใช้งาน
- จำกัดจำนวนครั้งการเข้าสู่ระบบผิดพลาด (Rate Limit / Lockout) เพื่อกัน Brute Force

### 6.4 นโยบายความปลอดภัยเครือข่าย (Network Security)

- **แบ่ง شبکه (Segmentation)** เป็นโซนอย่างน้อย: DMZ (Web/Portal) · Server LAN · Office LAN · Management (เครือข่ายอุปกรณ์) · Backup — กำหนด Firewall แบบ Default Deny
- Firewall ต้องใช้ **Allow-list** และปิดพอร์ต/บริการที่ไม่จำเป็นทั้งหมด
- **ห้าม** เปิด RDP/SMB สู่อินเทอร์เน็ตโดยตรง หากจำเป็นต้องผ่าน VPN หรือ Bastion Host ที่มี MFA
- ใช้ **Cloudflare** เต็มกำลัง: WAF · Rate Limiting · Bot Management · Turnstile · Geo-blocking · ซ่อน IP ต้นทาง · พิจารณา Cloudflare Tunnel แทนการเปิดพอร์ตสู่สาธารณะ
- บังคับใช้ **VPN + MFA** สำหรับการเข้าถึงระยะไกล ห้าม Split-tunnel โดยไม่ควบคุม
- แยก Wi-Fi สำหรับ Guest / พนักงาน / อุปกรณ์ IoT (ZKTeco, กล้อง) ออกจากกัน
- เปิดระบบตรวจจับการบุกรุก (IDS/IPS) และบันทึก Traffic ที่จุดสำคัญ
- ใช้ DNSSEC และกรอง DNS (บล็อก C2/โดเมนอันตราย)

### 6.5 นโยบายความปลอดภัยเซิร์ฟเวอร์และอุปกรณ์ปลายทาง (Endpoint & Server)

- ติดตั้งและปรับปรุง **แพตช์** ระบบปฏิบัติการและซอฟต์แวร์อย่างสม่ำเสมอ
- ใช้มาตรฐาน **Hardening** (อ้างอิง CIS Benchmark) กับ Windows Server และ Linux
- ติดตั้ง **EDR/Antimalware** บนทุกเครื่อง และอัปเดตฐานข้อมูลภัยคุกคามอัตโนมัติ
- เซิร์ฟเวอร์ต้อง **ไม่ใช้** งานทั่วไป (ท่องเว็บ/อีเมล/Office) และให้บริการด้วยบัญชีสิทธิ์จำกัด (ไม่รันเป็น root/administrator เต็มรูปแบบ)
- ปิด Autorun/USB และจำกัด Macro ใน Office
- บังคับ Auto-lock หน้าจอเมื่อไม่ใช้งาน (ไม่เกิน 5–10 นาที) และตั้งรหัส BIOS/UEFI ห้าม Boot จาก USB
- เก็บบันทึกเหตุการณ์ (Log) ของระบบและแอปพลิเคชันแบบรวมศูนย์ เพื่อการตรวจจับและสอบสวน
- ใช้ **Application Allow-listing** บนเครื่องที่ควบคุมได้

### 6.6 นโยบายความปลอดภัยแอปพลิเคชัน Odoo (Application Security)

- อัปเดต Odoo (19 และ 15) ตามรอบ **Security Patch** และติดตามช่องโหว่ (CVE) ของ Odoo และไลบรารีที่ใช้
- โมดูลที่พัฒนาขึ้นเอง (`custom_addons/`, `od19_*`) ต้องผ่านการตรวจสอบตามแนว **OWASP** ก่อนนำขึ้นใช้งาน:
  - ตรวจสอบ `ir.model.access` และ Record Rule ให้ครบถ้วน โดยเฉพาะ Portal ที่ต้องเห็นเฉพาะข้อมูลของตนเอง
  - ป้องกัน IDOR (เข้าถึงเรกคอร์ดข้ามเจ้าของ), Mass Assignment, Path Traversal ในรายงาน/ไฟล์แนบ
  - ตรวจ Controller ที่ `auth='none'` / `type='json'` ว่ามีการยืนยันตัวตนและตรวจสอบ input อย่างถูกต้อง
- ปิดช่องโหว่การสำรวจระบบ (Recon): ตั้ง `list_db=False` และ `dbfilter` ใน `odoo.conf` ปิดโหมด Debug/Web Editor บนระบบ Production
- จำกัดและตรวจสอบการอัปโหลดไฟล์ (ชนิด ขนาด ตำแหน่งจัดเก็บ) และสแกนไวรัสไฟล์ที่อัปโหลด
- บังคับใช้ Security Header (CSP, X-Frame-Options ฯลฯ) ผ่าน Cloudflare
- **API/Webhook** ต้องมี Token/Key, ตรวจสอบ Signature, เก็บ Secret ฝั่ง Server เท่านั้น (ห้ามส่งไป Client) และจำกัดอัตราการเรียก
- แยกสภาพแวดล้อม **Dev / Test / Production** ให้ชัดเจน ใช้ฐานข้อมูลและ credential คนละชุด ห้ามนำข้อมูลจริงไป Dev โดยไม่ปิดข้อมูลส่วนบุคคล (Masking)
- การอัปเกรด/เปลี่ยนแปลงฐานข้อมูล ต้องหยุดบริการ สำรองข้อมูลก่อน และทดสอบบนสภาพแวดล้อมทดสอบทุกครั้ง

### 6.7 นโยบายการจัดการข้อมูลและการจำแนกชั้นข้อมูล (Data Classification & Handling)

- ข้อมูลทุกประเภทต้องถูก **จำแนกชั้น**: Public / Internal / Confidential / Secret
- ข้อมูลส่วนบุคคล ข้อมูลเงินเดือน เอกสารภาษี และข้อมูลลูกค้า จัดเป็น **Confidential ขึ้นไป**
- กำหนดผู้เป็น **เจ้าของข้อมูล** และผู้มีสิทธิ์เข้าถึงตามหน้าที่
- บังคับใช้หลัก **Data Minimization** — เก็บเท่าที่จำเป็น และลบ/ทำลายตามระยะเวลาเก็บรักษาที่กำหนด (สอดคล้อง PDPA)
- ควบคุมการส่งข้อมูลออกภายนอก (DLP) โดยเฉพาะข้อมูลชั้น Confidential ห้ามคัดลอกออกผ่าน USB/อีเมลโดยไม่ได้รับอนุญาต
- ข้อมูลที่ต้องเปิดเผยต่อสาธารณะ/คู่ค้า ต้องผ่านการอนุมัติและปิดข้อมูลส่วนบุคคลก่อน

### 6.8 นโยบายการเข้ารหัสข้อมูล (Cryptography)

- เข้ารหัสข้อมูลขณะจัดเก็บ (**Encryption at Rest**) บนเซิร์ฟเวอร์และอุปกรณ์พกพา (เช่น BitLocker / LUKS)
- เข้ารหัสข้อมูลขณะส่ง (**Encryption in Transit**) ด้วย TLS 1.2 ขึ้นไปทุกจุด (รวม Cloudflare Edge → Origin แบบ Full/Strict)
- จัดเก็บกุญแจและความลับ (Secrets/API Keys) ในที่ปลอดภัย เข้าถึงได้จำกัด ห้ามฝังในโค้ดหรือส่งไป Client
- การส่งข้อมูลชั้น Confidential ออกนอกองค์กร ต้องผ่านช่องทางที่เข้ารหัสและได้รับอนุมัติ

### 6.9 นโยบายการสำรองข้อมูลและกู้คืน (Backup & Recovery)

- ปฏิบัติตามหลัก **3-2-1**: สำเนา 3 ชุด · สื่อ 2 ประเภท · เก็บนอกสถานที่ 1 ชุด
- จัดทำ **Immutable / Offline Backup** เพื่อป้องกันการเข้ารหัสข้อมูลสำรองจาก Ransomware
- **ทดสอบการกู้คืนจริง** เป็นรอบอย่างน้อยทุก 3–6 เดือน และบันทึกผล
- กำหนดเป้าหมาย **RTO/RPO** ต่อระบบ (โดยเฉพาะ Odoo) และบันทึกเป็นเอกสาร
- ข้อมูลสำรองต้องเข้ารหัสและควบคุมการเข้าถึงเทียบเท่าข้อมูลต้นฉบับ
- จัดทำ Runbook การกู้คืนที่ผู้อื่นสามารถทำแทนได้

### 6.10 นโยบายความปลอดภัยทางกายภาพและสิ่งแวดล้อม (Physical & Environmental)

- ห้องเซิร์ฟเวอร์/ตู้แร็ค ต้องล็อก ควบคุมการเข้าถึงด้วย Access Control พร้อมบันทึก และมีกล้องวงจรปิด
- จัดให้มีระบบ UPS ระบบดับเพลิง การควบคุมอุณหภูมิ/ความชื้น
- ห้ามนำอุปกรณ์บันทึกข้อมูลส่วนตัว (USB/External Drive) มาเชื่อมต่อโดยไม่ได้รับอนุญาต
- เอกสารที่มีข้อมูลชั้น Confidential ต้องถูกจัดเก็บในที่ล็อก และทำลายด้วยเครื่องทำลายเอกสารเมื่อไม่ใช้
- ทำลายสื่อบันทึกข้อมูล (ฮาร์ดดิสก์/SSD) อย่างปลอดภัยก่อนทิ้งหรือส่งซ่อม
- ห้ามปล่อยเครื่องที่ล็อกอินค้างไว้โดยไม่มีผู้ดูแล

### 6.11 นโยบายอุปกรณ์พกพาและการทำงานระยะไกล (Mobile & Remote Work)

- อุปกรณ์ที่ใช้ทำงานระยะไกลต้องมี Full-disk Encryption, EDR และผ่านการปรับปรุงแพตช์
- การเข้าถึงระบบของบริษัทจากภายนอก ต้องผ่าน **VPN + MFA** เท่านั้น
- **ห้าม** ใช้เครื่องส่วนตัว (BYOD) เข้าถึงระบบ Production โดยไม่ได้รับอนุมัติและไม่มีมาตรการควบคุม
- ห้ามใช้ Wi-Fi สาธารณะโดยไม่ผ่าน VPN
- รายงานทันทีเมื่ออุปกรณ์สูญหายหรือถูกขโมย เพื่อระงับการเข้าถึงและล้างข้อมูลระยะไกล

### 6.12 นโยบายห่วงโซ่อุปทานและบุคคลที่สาม (Supply Chain & Third-Party)

- ประเมินความปลอดภัยของซอฟต์แวร์ แพ็กเกจ และไลบรารีของบุคคลที่สาม (รวมโมดูล OCA) ก่อนนำมาใช้
- ตรึงเวอร์ชัน (Pin Version) และตรวจสอบความถูกต้อง/ความสมบูรณ์ของ Dependency
- ผู้ให้บริการภายนอกที่เข้าถึงระบบ ต้องมีข้อตกลงรักษาความลับ (NDA/DPA) และใช้บัญชีเฉพาะกิจที่มีอายุจำกัด
- ทบทวนสิทธิ์และการเข้าถึงของบุคคลที่สามเป็นรอบ และยกเลิกทันทีเมื่อสิ้นสุดสัญญา

### 6.13 นโยบายความปลอดภัยของระบบ AI ภายในเครื่อง (AI Security)

- ข้อมูลชั้น Confidential ห้ามส่งเข้าโมเดลภายนอกโดยไม่ได้รับอนุมัติ ให้ใช้โมเดลที่รันภายในเครื่อง (Ollama) เป็นหลัก
- ป้องกัน **Prompt Injection** ด้วยการตรวจสอบ/ทำความสะอาด input และจำกัดการกระทำ (Tools/Actions) ที่ AI เรียกใช้ได้
- AI ต้องแสดงผลตามสิทธิ์ของผู้ใช้ที่ร้องขอ และห้ามเข้าถึงข้อมูลเกินสิทธิ์
- การกระทำที่เปลี่ยนแปลง/ลบข้อมูลจริงโดย AI ต้องมีการอนุมัติโดยมนุษย์ (Human-in-the-Loop)
- บันทึกการใช้งาน AI เพื่อการตรวจสอบย้อนหลัง

### 6.14 นโยบายการจัดการเหตุการณ์ความปลอดภัย (Incident Management)

- ทุกคนมีหน้าที่ **รายงานเหตุการณ์ทันที** ที่พบหรือสงสัย
- มี **แผนตอบสนองเหตุการณ์** กำหนดบทบาท ขั้นตอน (Contain → Eradicate → Recover → Learn) และช่องทางติดต่อ
- จัดทำ **Playbook** สำหรับเหตุการณ์สำคัญ: Ransomware · ข้อมูลรั่วไหล · DDoS · บัญชีถูกยึด · อุปกรณ์สูญหาย
- เก็บรักษาหลักฐาน (Log/Image) เพื่อการสอบสวนก่อนดำเนินการล้างระบบ
- กรณีข้อมูลส่วนบุคคลรั่วไหล ต้องประเมินและแจ้งตามกรอบเวลาที่ PDPA กำหนด
- จัดทำรายงานสรุปบทเรียน (Post-Incident Review) และปรับปรุงมาตรการ

### 6.15 นโยบายการปฏิบัติตามกฎหมายและข้อกำหนด (Compliance)

- ปฏิบัติตามกฎหมายที่เกี่ยวข้อง รวมถึง PDPA และกฎหมายด้านภาษี/บัญชีของประเทศไทย
- ให้ความร่วมมือกับหน่วยงานกำกับดูแลและการตรวจสอบภายใน/ภายนอก
- ทบทวนนโยบายและมาตรการให้สอดคล้องกับกฎหมายที่เปลี่ยนแปลง

### 6.16 นโยบายการสร้างความตระหนักและการฝึกอบรม (Awareness & Training)

- อบรมความปลอดภัยสารสนเทศให้พนักงานทุกคนในวันเริ่มงาน และทบทวนอย่างน้อยปีละ 1 ครั้ง
- จัดทดสอบ **Phishing Simulation** อย่างสม่ำเสมอและให้ผลป้อนกลับเพื่อการเรียนรู้
- อบรมเฉพาะทางสำหรับผู้ดูแลระบบและผู้พัฒนา (Secure Coding, การใช้ AI อย่างปลอดภัย)
- เผยแพร่นโยบายและคู่มือการปฏิบัติให้พนักงานเข้าถึงได้ง่าย

## 7. การบังคับใช้ (Enforcement)

7.1 นโยบายนี้มีผลบังคับใช้กับทุกหน่วยงานและพนักงานทุกคนในบริษัท

7.2 การฝ่าฝืนอาจนำไปสู่การดำเนินการทางวินัย ทางแพ่ง และ/หรือทางอาญา ตามความเหมาะสมและตามกฎหมาย

7.3 ผู้ให้บริการภายนอก/ผู้รับเหมา ที่ฝ่าฝืนอาจถูกระงับสัญญาและการเข้าถึงระบบ

---

## 8. การทบทวนและการปรับปรุง (Review & Improvement)

8.1 ทบทวนนโยบายนี้อย่างน้อย **ปีละ 1 ครั้ง** หรือเมื่อมีการเปลี่ยนแปลงที่สำคัญ (กฎหมาย เทคโนโลยี โครงสร้างองค์กร หรือหลังเกิดเหตุการณ์รุนแรง)

8.2 การปรับปรุงให้แก้ไขเวอร์ชัน (R00 → R01 → …) พร้อมระบุวันที่ปรับปรุงล่าสุดที่หัวเอกสารเสมอ

8.3 จัดให้มี **การตรวจสอบภายใน (Internal Audit)** และ **การทบทวนโดยผู้บริหาร (Management Review)** ตามรอบ เพื่อความสอดคล้องกับ ISO/IEC 27001

## 9. ตัวชี้วัดความสำเร็จ (KPIs)

| ตัวชี้วัด | เป้าหมาย |
|---|---|
| ความครอบคลุม MFA ของบัญชีสำคัญ | ≥ 95% |
